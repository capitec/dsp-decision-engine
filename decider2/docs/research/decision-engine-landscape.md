# Decision-engine landscape: credit granting and fraud

**Date:** 2026-09-20
**Status:** research note (not a design doc; nothing here is a decision)

## 1. Purpose and how to read

decider2 is a numba-first decision engine for bank credit-granting logic and transaction-fraud interdiction. Before its authoring model, governance surface and interchange formats are frozen, it is worth knowing what the rest of the field does: which products a bank would otherwise buy or embed, how they let people author rules (tables, trees, graphs, DSLs, code), which standards they implement (OMG DMN/FEEL, GoRules JDM, PMML), how they deploy and execute (embedded library, REST, batch, streaming), what they publish about latency, and what governance they offer (versioning, audit, simulation, champion/challenger, approvals). The three engines the user named as reference points — GoRules JDM/ZEN, SAS Intelligent Decisioning and the SAS Viya platform it runs on — get the most depth, and JDM gets its own section (§8).

**How to read.** Every factual claim carries a link to the source that owns it: vendor documentation, a GitHub repository, a registry page, or the OMG specification. Analyst reports, blogs and third-party summaries were used only to discover candidates, never as the cited source. Where a vendor page could not be fetched (bot walls, JavaScript-only shells, 403s, login walls) the item is marked **unverified** rather than dropped or asserted. Performance numbers are quoted only from vendor-owned pages, with the URL, and are vendor claims — none were independently measured. "SA adopter" means the vendor states the customer on its own site; absence means "none found on the vendor's site", not "none exist". Fetching was done on 2026-09-20; all pages are quoted as they read that day. §10 lists every URL that was fetched and every one that failed.

## 3. Bank-specialist commercial credit-decisioning platforms

Depth for the ones a bank building its own engine would most plausibly be measured against; one paragraph each for the rest.

#### SAS Intelligent Decisioning (on SAS Viya)

- **Vendor / licence:** SAS Institute; commercial subscription. Runs only on the SAS Viya platform, which SAS describes as "a unified data and AI platform that connects data, builds and governs models, and operationalizes decisions" and which "supports Python, R, Java, Lua and REST APIs" ([sas.com/viya](https://www.sas.com/en_us/software/viya.html)).
- **Domain fit:** both credit and fraud; the product page names bank customers (Nexent Bank, VietCredit, S-Bank) ([product page](https://www.sas.com/en_us/software/intelligent-decisioning.html)).
- **Authoring:** "Low-code, graphical drag-and-drop" decision builder; a decision flow combines rule sets, analytical models, treatment groups, custom code files (Python, SAS, DS2), subdecisions and conditional branches (Yes/No, Equal, Range, Like); lookup tables with activation and locking ([features list](https://www.sas.com/en_us/software/intelligent-decisioning/features-list.html); node inventory quoted from the SAS Tutorials PDF listing at [documentation.sas.com](https://documentation.sas.com/api/collections/edmcdc/v_024/docsets/edmqs/content/edmqs.pdf?locale=en) — full PDF not fetched).
- **Standards:** open-source Python models can be included "without translation" via code nodes; SAS Model Manager integration. No DMN/FEEL claim found. PMML/ONNX import is a Model Manager feature (unverified from the pages fetched).
- **Deployment:** Azure, AWS, Google Cloud, hybrid, on-prem; "OCI-compliant containers (SAS Container Runtime)"; publishing destinations: Micro Analytic Service (MAS) REST, SAS Container Runtime, CAS batch, in-database Hadoop/Teradata, in-stream via Event Stream Processing ([features list](https://www.sas.com/en_us/software/intelligent-decisioning/features-list.html)).
- **Execution / published numbers:** "batch, API and real-time execution"; "More than 7,000 real-time transactions per second" and "Response times of 5 to 10 milliseconds per transaction" ([features list](https://www.sas.com/en_us/software/intelligent-decisioning/features-list.html)) — hardware/decision size not stated on that page.
- **Governance:** "Version control, change tracking, role-based approvals and governance workflows"; rule-fired data with detailed auditing; scenario testing with autogenerated validation tests; champion/challenger comparison; complete audit history ([product page](https://www.sas.com/en_us/software/intelligent-decisioning.html), [features list](https://www.sas.com/en_us/software/intelligent-decisioning/features-list.html)).
- **South African adopters on SAS's own site:** Absa — but for credit *risk reporting and model monitoring* on SAS Viya on AWS ("80% to 90% reduction in reporting time"); the release does not mention Intelligent Decisioning or origination ([press release](https://www.sas.com/fi_fi/news/press-releases/2026/august/absa-bank-modern-credit-risk.html)). Nedbank — SAS Office Analytics and Enterprise Miner for customer analytics, not decisioning ([Nedbank story](https://www.sas.com/en_za/customers/nedbank.html)). No Capitec, Standard Bank, FNB or TymeBank story on the SAS Africa customers page ([sas.com/en_za/customers](https://www.sas.com/en_za/customers.html)).

The truly stream-native designs (windowed aggregates computed inside the engine) are Feedzai Railgun and, by their stack statements, Hawk and Sift; everything else is request/response over pre-computed features, with batch as a separate mode. That split — stateless per-event evaluation over externally maintained features versus stateful windowing inside the engine — is the main architectural fork in the fraud set.

## 8. GoRules JDM deep-dive

JDM is the "JSON Decision Model" — the file format the open-source ZEN engine executes and the GoRules BRMS edits. Unlike DMN it is not an OMG standard; it is "a standard developed by GoRules Technologies" ([gorules.io/switch/drools](https://gorules.io/switch/drools)). The engine that runs it is MIT-licensed ([github.com/gorules/zen](https://github.com/gorules/zen)); the BRMS around it is commercial ([open-source scope](https://docs.gorules.io/developers/overview/open-source.md)).

### 8.1 Graph JSON shape

Source: [JDM Standard](https://docs.gorules.io/developers/jdm/standard) and [Node types](https://docs.gorules.io/developers/jdm/node-types.md).

- Two required top-level arrays: `"nodes"` and `"edges"`. Unknown top-level fields are ignored, so custom metadata can be carried alongside.
- Node object: `id`, `type`, `name`, `position` (`{x, y}` — editor layout only), `content` (type-specific).
- Edge object: `id`, `sourceId`, `targetId`, `sourceHandle` (the output port; used by switch branches).
- Execution is stateless: "JSON in, DAG traversal in topological order, JSON out" ([switch/drools](https://gorules.io/switch/drools)). There is no working memory, no re-firing, no salience.
- A Zod schema for the format ships in the `@gorules/jdm-editor` npm package ([JDM Standard](https://docs.gorules.io/developers/jdm/standard)); the MIT-licensed React editor is at [github.com/gorules/jdm-editor](https://github.com/gorules/jdm-editor).

### 8.2 Node types

The docs page lists seven; the Rust `zen_types::decision::DecisionNodeKind` enum (serde tag `"type"`) has eight — the docs omit `customNode`. Sources: [Node types](https://docs.gorules.io/developers/jdm/node-types.md), [docs.rs zen-types DecisionNodeKind](https://docs.rs/zen-types/latest/zen_types/decision/enum.DecisionNodeKind.html), [core/types/src/decision/mod.rs](https://raw.githubusercontent.com/gorules/zen/master/core/types/src/decision/mod.rs).

| `type` string | Purpose | `content` fields (as documented / as in source) |
|---|---|---|
| `inputNode` | Entry point; receives the object passed to `evaluate()` | optional `schema` (JSON Schema for validation) |
| `outputNode` | Exit point; returns the result | optional `schema` |
| `decisionTableNode` | Spreadsheet-style rules | `hitPolicy` (`"first"` \| `"collect"`), `inputs[]` (`id`, `name`, `field`), `outputs[]` (`id`, `name`, `field`, optional `type`), `rules[]` (each `_id` + column-id-keyed cell strings), plus `passThrough`, `inputField`, `outputPath`, `executionMode` |
| `expressionNode` | Map input object to a new object | `expressions[]` (`id`, `key`, `value` — a ZEN expression), plus the same transform attributes |
| `functionNode` | Custom JavaScript | `source` (v2 content is `{source}`; v1 was a bare string — `#[serde(untagged)]` in source). Runs on `rquickjs` (QuickJS) per [docs.rs zen-engine](https://docs.rs/zen-engine/latest/zen_engine/); "sandboxed, with `zod`, `big.js`, `dayjs`, `http` imports available" ([switch/drools](https://gorules.io/switch/drools)) |
| `switchNode` | Branching | `hitPolicy` (`"first"` \| `"collect"`), `statements[]` (`id`, `condition` — ZEN expression, `isDefault`). Under `collect` "the graph extends to all branches where conditions hold true" ([switch](https://docs.gorules.io/docs/switch)) |
| `decisionNode` | Invoke another JDM (sub-decision) | `key` (path resolved by a `DecisionLoader`), transform attributes |
| `customNode` | Host-defined node | `kind` (string), `config` (arbitrary JSON); dispatched to a `CustomNodeAdapter` in the host ([docs.rs zen-engine](https://docs.rs/zen-engine/latest/zen_engine/)) |

Decision table semantics ([Building decision tables](https://docs.gorules.io/learn/authoring/decision-tables.md)):
- `first` "evaluates rows top to bottom and stops at the first match"; `collect` "returns all matching rows as an array". A per-column collect variant uses a `[]` suffix on an output field.
- Input columns are either *targeted* (a `field` is configured, cells hold unary tests such as `> 6000`, `[1..10]`, `'a','b'`) or *generic* (`field` = `-`, cells hold full expressions).
- Output cells may be literals, expressions (`input.amount * 0.1`) or references.
- Only two hit policies exist. DMN's Unique / Any / Priority / Rule-order / Output-order and the `C+ C< C> C#` aggregations have no JDM equivalent.

### 8.3 Expression language (ZEN)

Sources: [syntax](https://docs.gorules.io/learn/zen-language/syntax), [functions](https://docs.gorules.io/learn/zen-language/functions.md).
- Arithmetic incl. `^`, comparisons, `and`/`or`/`not`, template strings `${...}`, slicing, `??` null-coalescing, ranges `in [1..10]`, ternaries, closures (`map`, `filter`, `some`, `all`, `one`, `none`, `count`, `flatMap`), math (`sum`, `avg`, `median`, `mode`, `rand`), string (`fuzzyMatch`, `matches`, `extract`), date (`d(...)`, `duration`), type (`string`, `number`, `bool`, `type`, `isNumeric`).
- Two modes: *standard* (expression nodes, output columns) and *unary test* ("shorthand syntax used in decision table input columns when a field name is defined"; the tested value is implicit, `$` refers to it inside function calls).
- GoRules' own comparison with FEEL: "FEEL and Zen share range and comparison syntax (`>= 18`, `[1..10]`), but built-in function names differ" ([switch/drools](https://gorules.io/switch/drools)).
- The docs do not state that ZEN is side-effect-free or non-Turing-complete; `rand()` exists, so pure determinism is not guaranteed by the language (unverified beyond the function list).

### 8.4 Engine, bindings, performance, trace

- Bindings: Rust crate `zen-engine`, Node `@gorules/zen-engine`, Python `zen-engine`, Go (`zen-go`), Java/Kotlin/.NET/Swift via UniFFI, WASM/WASI ([README](https://github.com/gorules/zen)). Crate v2.0.1 released 2026-08-22, MIT ([docs.rs](https://docs.rs/zen-engine/latest/zen_engine/)).
- Python API: `zen.ZenEngine()`, `create_decision(content)`, `evaluate(dict)`, `async_evaluate`, `evaluate_batch()`; loaders `static` / `fs` / `zip` / callback; `trace=True` returns per-node data and timing ([Python SDK](https://docs.gorules.io/developers/sdks/python.md)).
- Polars integration is row-at-a-time via `map_elements` calling a pre-compiled decision — not vectorised ([Polars integration](https://docs.gorules.io/developers/integrations/polars.md)).
- Published performance ([Performance](https://docs.gorules.io/developers/overview/performance.md)): "an average of 91,000 evaluations per second across 74 real-world decision benchmarks", single core, MacBook Pro M3; "Pure decision tables and expression nodes achieve 150K+ evaluations per second"; function nodes "3-50K req/s"; scenario figures include "Realtime fraud detection: 191K req/s" and "Loan approval: 45K req/s". Marketing copy elsewhere says "1M+ evaluations per second" with the Rust SDK ([docs intro](https://docs.gorules.io/docs/intro)) — a different, unexplained figure; treat the 91k benchmark page as the documented one.
- Trace: `EvaluationOptions` with trace returns `DecisionGraphTrace` / `EvaluationTrace` per node ([docs.rs](https://docs.rs/zen-engine/latest/zen_engine/)); the simulator shows "Which nodes executed, What data each node received, What each node produced, Which decision table rows matched" plus microsecond timing per node ([Test with simulator](https://docs.gorules.io/learn/authoring/testing.md)).

### 8.6 "Policies" — a second authoring form (2026)

Newer GoRules docs add *policies*: "a policy reads like a document: text and rule blocks mixed together"; blocks declare typed data models and write properties that other blocks read; "The engine works out execution order itself, from what each block reads and writes"; static checks reject `DUPLICATE_WRITER` and `CYCLIC_DEPENDENCY`; a policy is "a pure function over your data: an object goes in, and comes back enriched" ([Authoring policies](https://docs.gorules.io/learn/authoring/policies.md)). This is the closest thing in the GoRules world to decider2's declared-node, dependency-ordered module shape.

### 8.7 JDM versus DMN

| Aspect | DMN 1.5 (OMG formal/24-01-01, Jan 2024; 1.6 and 1.7 betas listed Sep 2024) | JDM |
|---|---|---|
| Owner | OMG, open standard, XML/XSD interchange (`DMN15.xsd`, `DMNDI15.xsd`) ([About DMN 1.5](https://www.omg.org/spec/DMN/1.5/About-DMN)) | GoRules; JSON; Zod schema in `@gorules/jdm-editor` |
| Model | DRD: decisions, input data, BKMs, knowledge sources; boxed expressions (literal, context, invocation, relation, list, function definition, decision table, and CL3 additions) | Flat DAG of 8 node types; no BKM / knowledge source concept |
| Expression language | FEEL (CL3) or S-FEEL (CL2); CL1 need not interpret expressions at all (DMN 1.5 §2) | ZEN; shares range/comparison syntax with FEEL, different function library |
| Hit policies | U, A, P, F, C (with `+ < > #`), R, O (DMN 1.5 §8.2.10) | `first`, `collect` (+ per-column `[]`) |
| Code escape hatch | Externally defined Java / PMML functions (DMN 1.5 §7) | `functionNode` (QuickJS JavaScript) and host `customNode` |
| Conformance | Three published conformance levels | None published |
| Execution semantics | Spec defines evaluation of DRG; engines vary (Rete-based Drools, sequential Camunda) | Single stateless traversal, defined by the reference engine |

Sources for the DMN column: OMG DMN 1.5 PDF fetched locally (clause 2 conformance text, §8.2.10 hit policies, §7 boxed expressions) — [omg.org/spec/DMN/1.5/PDF](https://www.omg.org/spec/DMN/1.5/PDF); version list from [omg.org/spec/DMN/](https://www.omg.org/spec/DMN/).

## 9. Observations relevant to decider2

1. Nothing surveyed occupies decider2's exact niche: a permissively licensed, Python-native engine that compiles per-record scalar logic and runs the same artefact in batch and single-record modes. The nearest shapes are jDMN (transpiles DMN to Java/Kotlin/Python — compile-ahead), GoRules ZEN (stateless DAG, per-node trace, Python binding, but a per-row FFI call under Polars `map_elements`, not vectorised), SAS Intelligent Decisioning (one decision published to MAS real-time, CAS batch and ESP streaming) and ACTICO (Java embed plus batch CLI, trace to Kafka).
2. Every serious commercial product exposes the same three authoring primitives — decision tables, decision trees/flows, scorecards — and the same governance quartet: versioned artefacts, per-decision trace or "rule-fired" record, simulation/backtest before release, and champion/challenger routing. FICO, SAS, ACTICO, Sparkling Logic, Experian and Equifax all state all four. That is the bar a bank-internal engine will be measured against.
3. Hit-policy vocabulary is stable across the field: DMN's Unique/Any/Priority/First/Collect, JDM's first/collect, AWS's FIRST_MATCHED/ALL_MATCHED, DecisionRules' FIRST_MATCH/EVALUATE_ALL, Nected's First/Unique/Collect/Order. Naming decider2's table semantics in those terms costs nothing and eases import.
4. Import worth supporting: DMN decision tables at Conformance Level 2 (S-FEEL unary tests: comparisons, ranges, lists, `-`) cover what FICO, Trisotech, Drools, Camunda and Signavio export, and JDM `decisionTableNode` is a strict subset of that (unary tests in the same range syntax, two hit policies). Full FEEL (CL3) is a much larger surface and no fraud vendor uses it.
5. Export worth considering: a JDM document is small, JSON and has an MIT React editor and a simulator — a cheap path to a visual view of a decider2 module; DMN XML gives Trisotech/Drools/Camunda tooling and the TCK for table-semantics testing.
6. Published latency claims cluster at 5–25 ms for hosted decisioning (SAS 5–10 ms, Sardine ~25 ms, DataVisor <100 ms) and sub-millisecond only for in-process engines (ZEN µs/op, Higson 0.23 ms). decider2's measured single-record budget work (EXPERIMENTS.md N-series) is already in the in-process class.
7. Stream-native windowing (Feedzai Railgun, Hawk, Sift) is the one architectural capability no per-record engine in this survey has; treating windowed features as inputs computed upstream (Polars) is the pattern every other vendor follows.
8. South African evidence on vendor sites is thin: TymeBank (GDS Link) is the only named SA bank for decisioning; Absa appears at SAS (credit-risk reporting), ACI (P2P) and Fiserv (cards) but not for decisioning or fraud rules.
