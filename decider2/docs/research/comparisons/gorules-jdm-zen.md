## 1. Structural side-by-side

| Concept | GoRules | decider2 |
|---|---|---|
| **Artefact** | One JSON document: `{nodes: [], edges: []}`, nothing else required (`zen/core/types/src/decision/mod.rs:9-12`). Unknown top-level and node-level fields are ignored by serde, so metadata rides along. | Python objects. `Module` = `name` + `tuple[Step, ...]` + `params_model` + `relabel_reads/writes` + `bound` + `contract` (`decider2/src/decider2/types.py:70-83`). Composition `Pipeline` of modules (`graph/pipeline.py:29-46`). Interiors (tables, trees) are pydantic **documents** that build into `Module`s. |
| **Graph / DAG model** | Explicit `nodes` + `edges`; `edge = {id, sourceId, targetId, sourceHandle?}` (`mod.rs:16-21`). `petgraph::StableDiGraph`, walked from the input node, each node fired once all incoming neighbours are visited (`zen/core/engine/src/decision_graph/walker.rs:143-248`). Node `position {x,y}` exists in the editor type but is absent from the engine's Rust struct — layout is ignored at runtime. | No edges at all. Inside a module, order is **inferred** by matching a step function's parameter names to sibling steps' output names, then `graphlib.TopologicalSorter` (`graph/interface.py:112-146`: *"ordering is derived by topological sort — you never declare execution order"*). Across modules, `\|` is literal written order (`graph/pipeline.py:2-6`: *"`\|` is a sequence, not a dependency-resolved graph"*), with an unresolved leaf name resolving to the most recent producer ("the waterfall", `pipeline.py:306-393`). |
| **Data flow between nodes** | **One merged JSON object.** All incoming nodes' outputs are merged (`walker.rs:126-141`, `merge_clone`) into the node's input; there are no typed ports. `sourceHandle` is used *only* to pick switch branches. Any node can also reach any other by name via `$nodes.<NodeName>.<field>` when `nodes_in_context` is on, default true (`walker.rs:95-114`, `zen/core/engine/src/config.rs:14`). Final result = merge of all sink nodes (`graph/graph.rs:297`, `walker.rs:81-93`). | Flat string-keyed registry of numpy arrays: `Registry = dict  # name -> np.ndarray, plus "__valid__<name>" companions` (`runtime/modes.py:51`). Each output is written twice — bare name plus `f"{step.name}@{owner}"` for the version chain (`runtime/modes.py:83-84`, `compile/driver.py:412-415`), which is decider2's `$nodes`-equivalent and is `.emit("term_cap@sector_cap")`-addressable (`graph/pipeline.py:144-155`). |
| **Node types** | Eight, serde-tagged on `"type"` (`mod.rs:42-69`): `inputNode`, `outputNode`, `functionNode`, `decisionNode` (sub-decision by key), `decisionTableNode`, `expressionNode`, `switchNode`, `customNode`. Plus four transform attributes on most of them: `inputField`, `outputPath`, `executionMode: single\|loop`, `passThrough` (`mod.rs:206-225`). | One graph type (`Module`). Inside interiors, typed classes: table expressions `and / or / between / in / is_true / eq` (`tables/schema.py:246-545`); tree nodes `LeafNode / UnaryNode / CasesRanges / CasesStringMatch / CasesIsIn / CompositeNode` (`trees/schema.py:952-962`). `Branch` and `Loop` are specified but **not implemented** (`docs/03-authoring-api.md`, "NOT BUILT (review finding 7, 2026-09-20)"). |
| **Decision table — columns** | `inputs[] = {id, name, field?}`, `outputs[] = {id, name, field, type?}` (`mod.rs:127-151`). `name` is a free-text reviewer label distinct from the technical `field` — e.g. `{"id":"i1-1","name":"On-time Payment Percentage","field":"account.payment_history.on_time_payment_percentage"}` (`zen/benchmark/fixtures/graphs/credit-limit-adjustment.json`). Rules are `HashMap<columnId, cellString>` plus reserved `_id` and `_description` (`mod.rs:111`, `nodes/decision_table/mod.rs:362-376`). | `ParametersConfig{data: List[Dict], dtypes}` — the rows as plain data, deliberately not a polars subclass (`tables/schema.py:152-196`); `expression: Expression`; `outputs: List[str]`; `default: List[Any]` (`tables/schema.py:551-571`). Columns are referenced by data-frame column name only — **there is no reviewer-facing column label**. |
| **Decision table — hit policies** | Two: `first` (default) and `collect` (`mod.rs:119-125`, `DecisionTableHitPolicy`). Plus **per-column collect**: an output `field` ending `[]` collects across all matching rows while other columns stay first-hit (`mod.rs:153-161` `write_path()`, dispatched at `nodes/decision_table/mod.rs:38-46`). Unmatched → `Variable::Null` for `first`, `[]` for `collect` (`mod.rs:69-72`, docs). | One, hard-coded: first match wins, closing on `default` (`tables/schema.py:561-563`). Codegen emits a row scan returning the matched index or the literal `-1`, and each output function does `if {row_fn} < 0: return shared.{default_key}[0]` (`tables/codegen.py:207-219, 267-268`). No `collect`, no per-column collect. |
| **Decision table — wildcard** | **Empty cell = matches anything**, and a missing key for a column also matches: `let Some(rule_value) = rule.get(&input.id) else { return true }; if rule_value.is_empty() { return true }` (`nodes/decision_table/mod.rs:151-175`, again at `:302-307`). There is no `-`/`*` token; `-` is only a docs convention for marking a column *generic*. A trailing all-empty row is the documented catch-all. In **match blocks** the wildcard is spelled `_` (`policy/blocks/match_block.rs:234`). | No wildcard sentinel of any kind. "Don't care" is structural: a `BetweenExpression` with only one of `lower_bound_column`/`upper_bound_column` is open-ended (`tables/schema.py:300-401`). |
| **Decision table — ranges & cell grammar** | Cells are **ZEN unary tests** when the column has a `field` (the tested value is implicit, `$` refers to it), and full standard expressions when `field` is empty (`nodes/decision_table/mod.rs:162-174`: `run_unary` vs `run_standard`). Accepted forms: `>= 95`, `<= 0`, `[18..65]` inclusive, `(0..100)` exclusive, lists `'US','CA','GB'`, `> 10 and < 50`, `len($) > 5` (docs.gorules.io/learn/authoring/decision-tables.md). Numeric/string/bool literal cells are indexed into a bitset for row pruning above 8 rows (`nodes/decision_table/index.rs:9,53-129`). | No cell string grammar and no parser. Conditions are typed pydantic instances; `BoundMode` has exactly two members, `lower_inclusive` = `[lo,hi)` and `upper_inclusive` = `(lo,hi]` — *"`both_inclusive`/`both_exclusive` are intentionally omitted"* (`trees/schema.py:119-139`). Boolean structure is normalised to DNF, capped at 64 disjuncts (`tables/schema.py:222-297`). |
| **Decision table — output typing** | Optional per-column `type`: `string \| number \| boolean \| date \| <dictionaryName>`, each optionally `[]` (`policy/blocks/decision_table.rs:126-156`). Output cell values are ZEN expressions evaluated in the row's scope (`nodes/decision_table/mod.rs:413-428`), written by dotted path (`dot_insert`). | Outputs are declared column names validated against `parameters.columns` (`tables/schema.py:576-581`). Numeric/boolean outputs compile to kernel functions reading a `shared` array by matched-row index; **string outputs are not compiled** — they are mapped back in polars after the fact via `replace_strict` (`tables/build.py:62-90`). |
| **Trees** | No tree node type. A tree is expressed as a `switchNode` chain, or as a policy `match` block (`key` + `arms[] = {id, condition, value}` — `policy/blocks/match_block.rs:30-45`). | First-class `Tree` document: `nodes`, `edges` (camelCase `sourceIndex` kept "so UI documents round-trip"), `output`, `format_version: Literal[3]` (`trees/schema.py:1055-1136`). Compiled to nested `if/elif/return` Python, caps at `LINE_CAP = 500` and `_MAX_NESTING = 90` (`trees/codegen.py:80-93`). Every threshold is `Threshold = Union[float, int, InputRef]` and becomes a **kernel argument, never a literal** (`trees/schema.py:245-251`, `trees/codegen.py:214-231`). |
| **Expressions / params** | ZEN expression language, own crate. Two parse modes — standard and unary test (`intellisense/mod.rs:390-416`). Function library, verbatim from the enums: closures `all, none, some, one, filter, map, flatMap, count` (`zen/core/expression/src/functions/mod.rs:47-58`); internals `len, contains, flatten, merge, mergeDeep, upper, lower, trim, startsWith, endsWith, matches, extract, fuzzyMatch, split, abs, sum, avg, min, max, rand, median, mode, floor, ceil, round, trunc, isNumeric, string, number, bool, type, keys, values, d` (`functions/internal.rs:9-55`); date methods `add, sub, set, format, startOf, endOf, diff, tz, isSame, isBefore, isAfter, isSameOrBefore, isSameOrAfter, second…year, timestamp, offsetName, isValid, isYesterday, isToday, isTomorrow, isLeapYear` (`functions/date_method.rs:10-46`). Every expression is typed and type-checked, with a **strict/loose nullability mode** (`intellisense/mod.rs:61-76`; ~1050 lines of nullability conformance tests at `zen/core/expression/tests/data/analysis/nullable.toml`). No parameter concept — a "parameter" is just another field on the input object. | Params are declared in a step's own signature via `param(default, **field_kwargs)`, a carrier that *is-a* the default's type so the function stays plainly callable (`params.py:250-275`). Compiled into a real pydantic model with `extra="forbid"` — *"A misspelled param is a hard error… not silence"* (`params.py:455-476`). One flat namespace per module instance; overrides `params={"instance": {...}}` (`runtime/invoke.py:227-389`). `.bind()` freezes a knob but keeps it a runtime kernel argument (`graph/module.py:201-214`). No expression language anywhere — doc 08 §3.2 explicitly rejects one in config. |
| **Functions / custom logic** | `functionNode` runs JavaScript on QuickJS (`rquickjs`) with bundled `zod`, `big.js`, `dayjs` (`zen/core/engine/js/{zod,big,dayjs}.mjs`), a 5 s default timeout (`config.rs:15`) — and an **HTTP handler trait** so a function node can make network calls mid-decision (`zen/core/engine/src/nodes/function/http_handler.rs:9-37`). `customNode` dispatches `{kind, config}` to a host adapter (`mod.rs:227-232`). | The whole engine *is* custom logic: pure Python functions compiled by numba. Un-njit-able steps split out into a `FallbackSegment` run row-by-row in Python (`compile/driver.py:433-465`); no per-row `objmode` escape, because *"a nopython driver cannot call a Python function"* (doc 05 §6; measured escape costs 23.5×/77×/614.7×). |
| **Nulls & missing data** | Missing key on a table column = wildcard pass (`nodes/decision_table/mod.rs:156-161`). Failed reference read = row fails (`:315-318`). Expression type system models `Nullable(T)` and merges `T \| null` through ternaries (`nullable.toml`). At the graph level a `NullabilityDivergence` warning fires when an optional property is not declared nullable in the JSON Schema (`workspace/graph/analysis.rs:487-497`). | Four declared tiers: `REQUIRED / MISSING_AS / OPTIONAL / NOT_APPLICABLE_AS` (`types.py:14-21`), per input, with a `fill` for tiers 2/4. A REQUIRED null **routes the row to a decision** rather than raising — `Decision.REFER / DECLINE / RAISE`, default `REFER` with `reason: int = 4101` (`types.py:86-101`, `boundary/nulls.py:217-285`). OPTIONAL carries a separate validity mask; the kernel reads `{v} = {arr}[i] if {valid}[i] else None` (`compile/codegen.py:210-217`). `boundary/nulls.py:2-6`: *"The slot under a null contains leftover garbage, not zero."* |
| **Typing & schema** | Optional JSON Schema on the input and output nodes (`mod.rs:71-83`), validated at runtime, with dictionary references resolvable from imports (`graph/graph.rs:115-137`). Static type flow across the whole graph and across policies: 40 diagnostic codes (`workspace/types/diagnostic.rs:140-185`), emitted from ~2050 lines of analysis (`workspace/graph/analysis.rs`). | No author-declared interface; inferred `Interface(inputs, outputs, terminals, params_model, shared_fields)` (`types.py:58-66`, `graph/interface.py:46-179`) — *"0 of 204 corpus modules pass `outputs=`"*. Annotations map to a 4-entry dtype table: `bool→boolean, int→int64, float→float64, str→int32` codes; unannotated defaults to `float64` (`compile/driver.py:81-115`). Boundary admissibility is a **ladder, not a gate** — 3 tiers, 7 `EntryMode`s, nothing rejected; non-flat columns raise `NeedsKernelSplit` (`boundary/dtypes.py:76-119`). Verified at **400-in/633-out** (doc 01:526-528). |
| **Trace / explainability — graph** | `trace: bool` option. `DecisionGraphTrace{input, output, name, id, performance, traceData, order}` keyed by node id in a `HashMap` (`decision_graph/tracer.rs:77-92`). `performance` is a **formatted string** (`format!("{:.1?}", duration)`, `:43`) not a number. Table trace: `{index, reference_map, rule}` where `reference_map` is the field values actually read and `rule` maps `"<field>[<colId>]"` → the cell expression, plus `_id`/`_description` (`nodes/decision_table/mod.rs:357-400, 452-464`). Switch trace: the ids of the statements that held (`walker.rs:297-306`). Five trace serialisation modes incl. reference-deduplicated (`zen/core/engine/src/engine.rs:69-93`). **Caveat**: trace disables the decision-table row-pruning index (`nodes/decision_table/mod.rs:53-56, 111-113`), and the trace map is keyed by node id, so a node re-run under `executionMode: loop` overwrites its own trace. | No `observe/` package exists yet — `runtime/invoke.py:452-458` says `origin=`/`policy=` are *"accepted so the signature matches the spec, but not yet recorded anywhere"*. What exists: the `name@module` version chain; a tree's `<name>_path` int column (the leaf's `result_idx`) and a table's matched-row-index column, both ordinary emittable columns (`trees/codegen.py:445-465`, `tables/build.py:56-60`); build-time `explain()` (`trees/build.py:110-133`); `ServeHandle.gil_report()/health()`. The audit-record *shape* is specified (doc 04 §5.2, doc 08 §8) but unbuilt. |
| **Trace / explainability — policy** | Strictly better shape than the graph trace: `Trace{engine_version, properties, executions[]}` with per-block `BlockExecution{block_id, policy_path, instance_path, trace, operand_values, writes[{path, value}], reads[]}` and typed `BlockTrace` variants — `Assertion{result, conditions[{id,result}]}`, `DecisionTable{matched_rows[], evaluations[], extras}`, `Expression{property, value}`, `Match{matched_arm, value, arms[{id,result}]}` (`zen/core/engine/src/workspace/types/result.rs:13-102`). Duration is serialised as integer microseconds (`:22-27`). | — (as above) |
| **Versioning & content addressing** | Nothing in the engine. `engine_version` is stamped into a policy trace (`policy/evaluator.rs:141`). Document identity, branches, commits, pinned releases are the **commercial** BRMS (docs.gorules.io/brms/review/requests.md). | Content-addressed compiled artefacts: `sha256(source)[:16]` → `_gen_{digest}.py`, imported **by module name** so numba's on-disk cache survives a fresh process (`compile/cache.py:49-56, 91-129`). In-process `_DRIVER_CACHE` keyed on structure only — *"Params are NOT in the key and must never be"* (`compile/driver.py:494-533`). `structure_fingerprint(pipeline)` = sha256 over shape with every value excluded (`runtime/serve.py:90-115`). Three change classes values / interiors-shape / skeleton (`runtime/serve.py:50-56`, doc 08 §2). |
| **Batch vs single record** | Single record is the only primitive. `evaluate_batch(requests)` fans single evaluations across a worker pool sized by `available_parallelism()`, releasing the GIL (`zen/bindings/python/src/engine.rs:193-251`, `mt.rs:1-16`). ## 2. Feature inventory

"Have it?" is against decider2 as it stands on 2026-09-21 (`feature/decider-v2`, with the user's uncommitted edits).

| Feature | What it does | decider2 has it? | Worth adopting? |
|---|---|---|---|
| Single self-contained JSON artefact | Whole decision is one portable document with no code | partial — interiors are documents (`tables/schema.py:551`, `trees/schema.py:1055`) but the skeleton is Python by design | no — doc 08 §7.2 deliberately prefers generating code over widening config admission |
| Explicit `nodes`+`edges` wire model | Author draws the graph | no — order is inferred (`graph/interface.py:112-146`) | no — inference is decider2's differentiator; but see export (§4 #2) |
| Merged-object data flow | Downstream sees the union of upstream outputs | yes, functionally — flat name registry (`runtime/modes.py:51`) | n/a |
| `$nodes.<Name>.<field>` addressing of any earlier node | Read a specific producer's value, not the merged one | yes — `name@module` version chain (`runtime/modes.py:83-84`, `graph/pipeline.py:144-155`) | n/a — decider2's is stronger (typed, emittable) |
| Sub-decision node (`decisionNode` + loader) | Invoke another document by key | yes — module composition, `\|` | n/a |
| Transform attributes `inputField` / `outputPath` | Run a node against a sub-object and write the result to a path | no | maybe — `relabel_reads/writes` covers renaming but not sub-object scoping |
| `executionMode: loop` | Run a node once per element of an array input | no — `Loop`/`Each`/`grain` all unbuilt (doc 06 O5, "the most-invented gap") | yes — this is decider2's biggest known hole and GoRules shows a minimal form of it |
| `passThrough` | Merge a node's output over its input instead of replacing | yes implicitly (registry semantics) | n/a |
| Hit policy `first` | First matching row wins | yes, and it is the only one (`tables/schema.py:561`) | n/a |
| Hit policy `collect` | Return all matching rows | no | yes — fraud rule sets are natively "all rules that fired" (`example_projects/01`, `fired_rule_ids`) |
| Per-column collect `tags[]` | One column collects across all matches, others first-hit | no | yes — exactly the shape of `fired_rule_ids` + one scalar action |
| Empty cell = wildcard | Unconstrained column in a row | no sentinel at all (`tables/schema.py:300-401`) | yes — cheap, and every import format assumes it |
| `_` default arm | Explicit catch-all in a match/tree | partial — `LeafNode.result_idx = -1` and table `default` serve the purpose (`trees/schema.py:653-661`) | maybe — naming it `_` in the document would ease import |

## 3. What decider2 should borrow, ranked

**1. The trace triple: cell text + `reference_map` + per-condition booleans. Effort M.**
GoRules records, per fired row, the values actually read (`reference_map`), the cell expression per column keyed `"<field>[<colId>]"`, and for assertions/matches a per-condition `{id, result}` (`zen/core/engine/src/nodes/decision_table/mod.rs:357-400`; `zen/core/engine/src/workspace/types/result.rs:68-102`). decider2 today emits only the matched-row index. Doc 04 §6 failed *because* the reviewer could see a number but not the check: *"A reviewer cannot adjudicate a mismatch they are shown. They can only confirm a check the system already made"* (`docs/04:358`). A per-condition boolean *is* the check the system made. In decider2 this is nearly free: `EmittedCondition` already emits one `if ok and …` per condition (`tables/schema.py:384-400`), so an opt-in variant that writes each condition's result into a bit-packed int64 output column costs one array store per condition and stays inside the kernel. Touches `tables/codegen.py`, `trees/codegen.py`, and the unbuilt `observe/`.

**2. JDM as an export target, so jdm-editor is the free visual editor and simulator. Effort M–L.**
`@gorules/jdm-editor` 1.52.0 is MIT and bundles a WASM engine, so the simulator needs no backend (`jdm-editor/packages/jdm-editor/package.json`). A `DecisionTable` (`tables/schema.py:551`) maps onto a `decisionTableNode` mechanically; a `Tree` (`trees/schema.py:1055`) maps onto nested `switchNode`s or one table per level. The editor's diff model (`dg-types.ts:15-61`) and Excel round-trip come with it. Two honest caveats: export is lossy in the safe direction (decider2's four null tiers, `InputRef` thresholds and `NotApplicableAs` have no JDM home — park them in ignored fields, which JDM tolerates), and the simulator's answers are ZEN's, not decider2's, so it can be a *drawing and pointing* tool but must never be the source of truth for a number. Ship it behind `decider2 export --jdm` and a banner. Touches a new `decider2/export/jdm.py`, `docs/04` §6.5 ("every rendering is replaceable" — this is a rendering).

**3. Adopt the diagnostic model: codes, severity, structured location. Effort S for the frame, M to fill.**
`DiagnosticCode` is 40 `SCREAMING_SNAKE_CASE` values with `Severity error/warning/hint` and a location of `{policy_path, block_id, expression_id, span}` (`zen/core/engine/src/workspace/types/diagnostic.rs:129-185`). decider2 raises bare `ValueError` with prose (`graph/interface.py:27-43`). Prose is good for a CLI and useless to a UI, to a metric, or to a suppression list. Introduce `decider2/diagnostics.py` with a `Diagnostic(code, severity, location, message)` and route the six existing build errors plus the three lints through it, keeping today's message text verbatim. This unblocks doc 08 §6's `diff()`/`impact()` seam and doc 06 O21 (change class per field).

**4. Exhaustiveness and dead-branch checks on tables and trees. Effort M.**
Two checks, both computable from the document with no new machinery:
- Exhaustiveness: GoRules proves it over "every enum value, both booleans, or a gap-free numeric range" (`policy/blocks/match_block.rs:234`). decider2 already has half of it — `BetweenExpression.allow_gaps: bool = False` (`tables/schema.py:300-401`) and `resolved_bounds`. Extend to the whole expression tree and to `CasesRanges`, and emit `MISSING_DEFAULT_BRANCH` when neither exhaustive nor defaulted.
- `REDUNDANT_TABLE_ROW` and `NON_DISCRIMINATING_COLUMN` (`policy/linter/table_hygiene.rs:139-200`): a row shadowed by earlier rows, and a column whose removal changes no outcome. Both are pure functions of `ParametersConfig.data` plus the DNF form decider2 already computes.

**5. Hit policies: add `collect` and per-column collect. Effort M.**
JDM's `first`/`collect` plus the `field[]` suffix (`zen/core/types/src/decision/mod.rs:119-161`; dispatch at `nodes/decision_table/mod.rs:38-46`) is exactly the shape `example_projects/01-transaction-fraud-interdiction.md` needs: one scalar `action_code` plus a list-valued `fired_rule_ids`. decider2's table is hard-wired to first-match (`tables/schema.py:561-563`) and its codegen returns a single row index. A `hit_policy: Literal["first","collect"] = "first"` field plus, for `collect`, a bitmask output column (one int64 per 64 rows) keeps everything inside the kernel and inside numpy — no list dtype needed, decode to names in polars the way string outputs already are (`tables/build.py:62-90`). Name them `first`/`collect` because DMN, JDM, AWS Fraud Detector and DecisionRules all use that vocabulary (landscape note §9.3), which makes import free.

**6. A reviewer-facing label per column and a `description` per row. Effort S.**
JDM carries `name` (human) beside `field` (technical) on every table column and `_description` on every rule (`mod.rs:127-151`; `nodes/decision_table/mod.rs:362-376`). The credit fixture shows the effect: `"On-time Payment Percentage"` versus `account.payment_history.on_time_payment_percentage`. decider2's table columns are bare frame names. Adding `labels: Dict[str, str]` to `ParametersConfig` and `descriptions: List[str]` alongside `data` costs nothing at runtime, is carried straight into any rendering, and is the cheapest thing on this list that moves doc 04 §6.

**7. A `dictionary` concept: named, labelled, governed value sets. Effort M.**
`DictionaryDoc{name, entries[{id, value, label}]}` plus `DeclaredBase::Dictionary(name)` as an output column type (`policy/raw.rs:246-262`, `policy/blocks/decision_table.rs:113-156`) gives type-checked enums, editor dropdowns, and a `PREFER_DICTIONARY` hint when a column's cells are a small closed set. decider2 dropped a decline-reason taxonomy in v1 (doc 01 §5) and `MissingInputPolicy.reason: int = 4101` is currently a bare magic number (`types.py:94-101`). A `Dictionary` document referenced by name from table output columns and from reason codes fixes both.

**8. A wildcard/range cell *parser* — for import only. Effort S–M.**
Do not change decider2's semantics. Do accept, at the document boundary, the unary-test notation every other tool writes: empty cell, `>= 95`, `<= 2`, `[18..65]`, `(0..100)`, `'US','CA','GB'`. That notation is a strict subset of DMN S-FEEL and identical to JDM's, so one parser buys import from JDM, Camunda, Trisotech and Excel. Target the existing typed union (`tables/schema.py:246-545`); `[a..b]` becomes `BetweenExpression`, a list becomes `InExpression`, an empty cell becomes an absent condition. Note the semantic mismatch to document: `[18..65]` is both-inclusive, which decider2's `BoundMode` deliberately cannot express (`trees/schema.py:119-139`) — either widen `BoundMode` or reject both-inclusive on import with a clear message. Do not attempt to import `functionNode` or generic-column cells.

**9. A bounded `loop` / per-element execution mode. Effort L.**
`executionMode: "loop"` with `inputField`/`outputPath` (`mod.rs:206-225`) is a minimal, shipped answer to decider2's most-invented gap (doc 06 O5: nine different invented names across six projects; `Loop` still "NOT BUILT"). It is not a great answer — it is a per-node fan-out with no carry — but it is evidence that the bounded form is enough for real documents, which is worth knowing before designing `grain`/`Each`.

**10. Template strings for reason text. Effort S.**
`render_template(template, context)` and `${...}` interpolation (`zen/bindings/python/zen.pyi:91`) is how GoRules turns a fired rule into a sentence. decider2 has no mechanism to attach text to a decline reason. A literal-only template resolved *outside* the kernel, at write-back, keeps the kernel clean and gives doc 04's renderer something to render.

**Deliberately not ranked highly:** hit-policy naming (subsumed by #5), the row-pruning index (decider2's scan is already compiled, and GoRules disables theirs under trace anyway), strict/loose null modes (decider2's four tiers are more precise).

## 4. Where GoRules is a genuine alternative

**Where it wins outright: single-record serving of a small graph, today, with no build step.**

**[measured here]**, `credit-limit-adjustment` — 7 nodes, 3 decision tables, 2 expression nodes, on the fast path:

| path | ns/op |
|---|---|
| `engine.evaluate` with loader returning a precompiled `ZenDecisionContent` | **42 785** |
| `engine.evaluate` with loader returning the JSON string | 264 841 |
| `engine.evaluate` with loader re-reading the file | 291 127 |
| `ZenDecision.evaluate` after `create_decision(...)` | 1 407 692 |

Two things fall out. First, 43 µs end-to-end for a real credit table graph is 0.21% of decider2's own 20 ms budget (`docs/00-BUILD.md:25-26`) — plenty. Second, **the documented Quickstart pattern is the slowest one**: `create_decision` then `decision.evaluate` is 33× slower than the loader path, with byte-identical results, on `zen-engine 2.0.2`. That is either a binding defect or an undocumented trap; either way, anyone benchmarking ZEN from the README will get 1.4 ms and conclude wrongly. GoRules' own repo benchmark uses the loader path (`zen/benchmark/python/bench.py:15-29`) but re-reads the file each call, so it measures 291 µs.

Against GoRules' published figures — *"an average of 91,000 evaluations per second across 74 real-world decision benchmarks"*, single-core MacBook Pro M3, and *"Loan approval: 45K req/s"* (https://docs.gorules.io/developers/overview/performance.md) — 43 µs on an i7-14700HX through Python FFI is consistent.

**Where decider2 wins outright: batch, and width.**

- decider2: *"400-in/633-out mixed over 100k rows compiles, executes in 72 ms, answers a single record in 0.99 µs, and matches a numpy reference exactly"* (`docs/01-motivation-and-evidence.md:526-528`) — **0.72 µs/row** batch.
- ZEN **[measured here]**, same graph, N=20 000: serial loop 1 410 µs/row; `evaluate_batch` across 28 CPUs **86 µs/row** (16.3× speedup, so the parallelism is real). Using the fast single-record path as the serial baseline instead, ~43 µs/row serial → roughly 3–5 µs/row at 28 threads, best case.

So decider2's batch path is ~100× faster per row than ZEN's serial batch and still ~5–10× faster than ZEN's fully parallel batch, on a much smaller core count budget. And the documented Polars integration is worse than `evaluate_batch`: `pl.col("data").map_elements(evaluate_rules, return_dtype=pl.Utf8)` with `json.loads`/`json.dumps` inside the UDF (https://docs.gorules.io/developers/integrations/polars.md), i.e. one Python call, two JSON conversions and one FFI crossing per row, single-threaded. For a 100k-row nightly batch at 400-in/633-out that is not a contest.

**Where it is closer than the docs suggest, and this deserves attention.** decider2's *kernel* is 1 µs, but its *framework overhead* was measured at **971 µs p50 / 1048 µs p99 — 4.9–5.2% of a 20 ms budget** (`docs/01:872-887`), and N2 found a literal 400-kwarg call costs **1190 µs p50** versus **60.1 µs** for a dict (`docs/01:900-917`). Until the whole-row-marshal fix lands (projected **145 µs / 0.73%**), decider2's end-to-end single-record latency is *worse* than ZEN's 43 µs. That does not change the architecture verdict, but it does mean "we need decider2 because ZEN is too slow single-record" is not currently a true statement, and shouldn't be used as the argument.

**Where GoRules genuinely cannot serve decider2's stated scope.**

1. **Batch/real-time equivalence.** decider2's guarantee is mechanical — one compiled kernel, two entry points (`runtime/invoke.py:16-20`), backed by `interpreted ≡ stepped ≡ fused` (`testing/equivalence.py`). ZEN's equivalence is also mechanical (one engine), so this is *not* where it fails. Where it fails is the *cost* of the batch side, above.
2. **Replay.** `example_projects/09-governance-and-replay-harness.md:211` demands bit-identical replay with *"fewer than 0.05% of decisions non-reproducible."* ZEN ships `rand()` in its standard function library (`zen/core/expression/src/functions/internal.rs:34`) and an HTTP handler reachable from a function node (`zen/core/engine/src/nodes/function/http_handler.rs:9-37`). Neither is a blocker if you ban both, but nothing in the engine enforces the ban — so the ban becomes a review rule, which `example_projects/09` §5.15 is explicitly written to avoid.
3. **Width.** ZEN's unit of data is a JSON object. At 400 inputs and 633 outputs per record, every evaluation allocates and walks a 1000-key object tree. decider2's whole boundary design (`boundary/dtypes.py`, dtype-grouped 2D write-back, 100k chunking, 11.87 GB column-major at 1M rows — `docs/05:311-319`) exists because that shape does not fit a per-record JSON model.
4. **Numba fusion evidence.** Not applicable — ZEN has no native codegen; expressions run on a bytecode VM (`zen/core/expression/src/vm/vm.rs`). decider2's E7 finding that fusion is non-monotone (1 group 1.33–1.61× faster, 16 modules **0.17×**, `docs/01:290-313`) has no analogue and no relevance here.
5. **Credit-risk reviewer readability.** Genuinely a tie, and neither side has solved it. GoRules has the better *materials* — labelled columns, `reference_map`, per-condition results, a diffing editor, a simulator. decider2 has the better *finding*: two proxy-reviewer tests failed and doc 04 §6 concluded that *"Displaying a value is not the same as making it checkable"* (`docs/04:301`). Adopting GoRules' materials without that finding would reproduce their failure at higher fidelity.

**The honest verdict.** Running ZEN instead of decider2 is defensible for exactly one slice of the stated scope: a low-width, real-time-only, single-record decision — a fraud interdiction rule set on a few dozen fields, served at 43 µs, authored in a free MIT editor with a working simulator, with no compile step and no numba. For that slice it would be live in a week and decider2 will not be. It is not defensible for anything in `example_projects` that is batch-shaped, wide, or replay-certified. The right reading of GoRules is not "alternative engine" but **"finished versions of four things decider2 has specified and not built": a diagnostic model, a trace shape, a visual editor, and a table document format.**

## 5. What decider2 should deliberately not copy

1. **The `functionNode` JavaScript escape hatch.** QuickJS with a 5 s timeout and bundled `zod`/`big.js`/`dayjs` (`zen/core/engine/js/`, `config.rs:15`). It is the documented way to do anything the node types can't — and by GoRules' own numbers it drops throughput from 150K+ to *"3-50K req/s"* (performance page). decider2's equivalent is a Python step, which compiles. Adding a second, slower, unversioned, untyped logic language would undo doc 08's *"config may reference code by registered id. It may not contain code"* (`docs/08:49-50`).
2. **HTTP from inside a decision.** `HttpHandler` takes method, url, headers, body, auth (`nodes/function/http_handler.rs:16-29`). Any network read inside an evaluation makes the decision non-reproducible and puts a timeout on the request path. `example_projects/09` requires recorded reference-data versions and inputs captured as received; a live fetch defeats both.
3. **`rand()` in the rule language** (`functions/internal.rs:34`). Same reason. If champion/challenger needs randomness it must be an input with a recorded seed, not a function.
4. **Graph mutation during evaluation.** A switch node deletes losing edges, recursively deletes orphaned nodes, and restarts the walk, bounded by `ITER_MAX = 1_000` (`walker.rs:210-232, 271-295`), which forces a full graph clone per `DecisionGraph` (`graph/graph.rs:34, 92-94`). It is clever and it is why the trace is a map keyed by node id rather than an ordered list. decider2's compiled branch-as-a-flag is strictly better and already specified (doc 02 §7: *"branch-fired flag → `.emit()` → one int64 column, effectively free"*).
5. **`performance` as a formatted string.** `format!("{:.1?}", duration)` yields `"1.2µs"` (`decision_graph/tracer.rs:43`) — unparseable, locale-fragile, and unusable in a histogram. Their own policy trace does it correctly, as integer microseconds (`workspace/types/result.rs:22-27`). If decider2 records timing, record `int` µs.
6. **Trace keyed by node id.** `traces.insert(node.id.clone(), trace)` (`tracer.rs:58`) means a node executed twice — which `executionMode: loop` and the switch-reset path both allow — silently loses all but the last trace. Use an ordered list.
7. **Trace disabling an optimisation.** The row-pruning index is built only when trace is off (`nodes/decision_table/mod.rs:53-56, 111-113`). That makes the traced path a different code path from the untraced one, which is precisely what decider2's equivalence ladder exists to forbid. decider2's trace must be the same kernel with more columns emitted.
8. **Two hit policies and no more.** Borrow `collect`; do not conclude that two is the right number. But equally, do not import DMN's full set (`U A P F C R O` with `C+ C< C> C#`) — the landscape note already establishes no fraud or credit vendor uses the aggregating variants.
9. **Untyped `customNode` as the extension story.** `{kind, config}` dispatched to a host adapter, with the analyser conceding *"this node is not type-checked and downstream nodes are unchecked"* (`workspace/graph/analysis.rs:513-524`). decider2's fallback segment is honest by comparison: it names what fell back and expects the set to be *"empty in production"* (doc 08 §8).
10. **JDM as decider2's *internal* representation.** Exporting to it is item #2 above. Adopting it would mean losing the four null tiers, `InputRef` thresholds, the `name@module` version chain, dtype declarations, and `NotApplicableAs` — all of which are load-bearing and have no JDM slot. Lossy export, never lossy storage.

## 6. Corrections to the landscape note

The note (`decider2/docs/research/decision-engine-landscape.md` §8) is accurate except:

1. **§8.2 says `switchNode` statements have `isDefault`.** They do not, in this version: `SwitchStatement{id, condition}` only (`zen/core/types/src/decision/mod.rs:191-196`). A default branch is an empty `condition`, which `switch_statement_evaluate` treats as true (`walker.rs:261-269`).
2. **§8.2 says the wildcard/generic marker is `field = "-"`.** In the engine a column is generic when `field` is empty or absent, via `empty_string_is_none` (`mod.rs:133-135, 234-250`); `-` is a UI convention with no engine meaning. The row-level wildcard is an **empty cell** (`nodes/decision_table/mod.rs:156-161`).
3. **§8.6 calls policies a docs-only 2026 form.** Policies are fully implemented in the MIT engine — ~10 000 lines under `zen/core/engine/src/policy/` and `workspace/`, with 5 of the repo's 10 benchmark fixtures being policies (`zen/benchmark/manifest.json`). What is *missing* is the Python surface: policies cannot be loaded via `create_decision` (**[measured here]**: `RuntimeError: expected graph content, got policy`) and the entire `Workspace`/diagnostics API is Node-only (`zen/bindings/nodejs/src/policy.rs` vs nothing under `bindings/python/`).

Also worth adding to the note: `@gorules/jdm-editor` is **1.52.0, MIT**, and ships an in-browser WASM engine (`@gorules/zen-engine-wasm` 0.23.1), an Excel round-trip and a field-level diff model — i.e. the free editor is a real product, not a demo.

## 8. Open questions I could not settle

1. **Why is `ZenDecision.evaluate` 33× slower than `ZenEngine.evaluate` with a `ZenDecisionContent` loader** (1 407 692 vs 42 785 ns/op, byte-identical results, `zen-engine 2.0.2`)? I reproduced it four ways (`scratchpad/bench4.py`) but did not read enough of `bindings/python/src/decision.rs` to name the cause. If it is a per-call graph clone, the same cost may exist on other bindings. Unresolved, and material to any benchmark comparison.
2. **Is the policy authoring form reachable from Python at all beyond the loader path?** `create_decision` refuses policy content, and `bindings/python/src/` has no `Workspace`. Whether GoRules intends to add it — and therefore whether the 40 diagnostics are ever available to a Python shop — I could not determine.
3. **What is JDM's formal versioning story?** `FunctionNodeContent` is `#[serde(untagged)]` over a v2 `{source}` and a v1 bare string (`zen/core/types/src/decision/mod.rs:85-97`), and `zen/core/engine/js/v1/` exists, so there *is* a migration history — but I found no version field in the document and no documented compatibility policy. Round-tripping through a future jdm-editor is therefore an unquantified risk.
4. **Exactly which cell forms the row-pruning index recognises.** `ArmTest::{Enum, Bool, Number{cover}, Default, Unrecognized}` (`intellisense/discriminant.rs:9`) and `NumberCover::points()` decide it, and `Unrecognized` silently falls back to a full scan (`nodes/decision_table/index.rs:74-110`). I did not enumerate the recognised grammar, so I cannot say which cells cost a scan. Matters only if decider2 copies the index, which I recommend against.
5. **Whether the 74-scenario benchmark set is public.** The performance page cites 74 real-world decisions; the repo ships 10 fixtures (`zen/benchmark/manifest.json`). The other 64 are not in the MIT repo, so the 91 000 eval/s average cannot be independently reproduced.
6. **Whether `@gorules/jdm-editor` can be driven read-only against a decider2-generated document without a GoRules account.** `DecisionGraphProps` has `disabled` and `viewConfig` (README), and the WASM engine is bundled, which suggests yes — but I did not build and run the editor against a synthetic decider2 export, so the round-trip claim in recommendation 7 is untested.
7. **Whether ZEN's decision-table semantics pass the DMN TCK** for the subset they overlap on. No conformance statement exists on either side; this matters if decider2 wants one import parser to serve both JDM and DMN sources.
