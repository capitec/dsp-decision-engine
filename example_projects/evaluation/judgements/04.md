## 2. Similarity (2/5)

The two share only surface decomposition: modules named suppressions, overlays, arbitration and pre-assessment.

**Haiku** is one record per client, with all 60 campaigns handled inside a step `for` loop. Steps pass `List[Dict]` between each other (`pipeline.py:71-117`). Trees are Python dicts evaluated by a hand-written string parser (`tree_engine.py:283-330`).

**Sonnet** is one record per (client, campaign) and serves only campaign 23. It authors trees in a small internal model (`tree_model.py`), compiles them to a `TreeConfig` v3 document, and runs a pure-Python `walk()` for paths. Arbitration is a population-level pass outside decider (`arbitration.py`).

**The spec's worked example (§5.3.3, §5.4.1(d))** runs only in Sonnet, because Haiku has no campaign 23:
- `walk(TREE_V1, …, pre_assessed_amount=84000)` renders nodes 1→2(not held)→4→6→8→10→leaf 912 exactly as the spec does.
- Node 6 is a genuine two-parent DAG node with one identity.

On identity, Sonnet's node keys are content hashes (own condition plus parent key and direction) and survive export renumbering. Haiku's keys are sequential `node_N` (`tree_defs.py:88-96`), which is the export-order dependence §5.4.3 item 2 forbids.

## 3. Maintainability

**Haiku.** The code is short but misleading.
- `except Exception: return False` hides parse errors (`tree_engine.py:328`), and a missing feature silently becomes 0.
- The fill-in leaves use `hash(str)` (`tree_defs.py:103,116`), so trees differ between processes. With PYTHONHASHSEED=1 and 2, `generate_campaign_trees(5,1,5)` gives different md5s.
- The cap-reduction overlay runs before pre-assessment (`pipeline.py:219-227`). It scales an amount of 0, and `consume_pre_assessments` then overwrites the result, so the overlay never takes effect.
- All-campaign suppressions carry `campaign_id=None`, so a deceased client (id 10000) is still evaluated in 39 of 60 campaigns.
- Control assignment hashes `cycle_id` (`arbitration.py:380-392`), which moves clients every cycle. §5.7 requires a hash of (client, campaign, design version) that is stable across cycles.
- Tests are weak. For example, `assert len(reachable) >= len([root])` and `assert len(mapping) > 0`.
- NOTES claims node identity comes from "condition hashing". That is false.

**Sonnet.** The code is clear and well tested, but heavy with prose. Docstrings run to paragraphs and lean on cross-references into NOTES.md. Two docstrings are wrong:
- `suppressions.py:14-16` says "`pipeline.py` branches on `suppressed_absolute`". No branch exists: a deceased client with a fraud marker still gets leaf outcome TARGET and a R20 800 advertised amount (I ran this).
- NOTES says `walk()` captures the path "live". The served pipeline never calls it.

**Summaries.**
- **Haiku summary: 3.** It describes intent faithfully, and correctly flags that `amount_rule` is never evaluated and that the volume dial and cut-off shift are stubbed. It says trees are "deterministic" and suppressed campaigns are "skipped", and it misses the overlay ordering bug, the broken build and the `cycle_date_str` mismatch.
- **Sonnet summary: 4.** It is accurate on the served pipeline, the dual traversal and the two overlay mechanisms. It repeats the false "absolute suppressions (exclude from tree)" claim. It does not mention the identity map, the validator, the 59 generated trees or arbitration, and it does not notice that the path is not emitted.

## 4. Reuse

**Haiku: none.** 00 and 03 are on `PYTHONPATH` but never imported. `grep` finds no `credit_core`, `granting` or `core` imports, and `pre_assessment.py` is `random.Random` numbers. It used no `TreeConfig`, so `path_output` was never considered. Everything else is written from scratch: tree evaluator, suppressions, overlays and hashing (it does use stdlib `hashlib` for control).

**Sonnet: real.** The served sample shows 03's `solve_term` + `PriceEvaluator` running (`pre_assessment_evaluations = 12`, `BIND-AFF`) and 00's `build_appetite_table` running (`appetite_cell_id appetite@appetite-2026.09#10|1|5`). It also calls:
- 00's `eligibility` and `consent` steps
- 00's `AdjustmentRegister.apply_stack`, whose tighten-only rule is reused for the cap reduction
- 00's `generate_flex_loan_card`, via `generate_configs.py`

The one approximation is `max_affordable_instalment = discretionary × 0.30` in place of 02, which is declared.

**TreeConfig / `path_output`.** Sonnet used TreeConfig well:
- It read the docstring, concluded that `path_output` yields only the terminal leaf id, and said so (NOTES §4.1).
- Its nodes are named by content-derived `node_key`, so `path_output="leaf_key"` emits a stable leaf key.
- It runs the tree twice with `.named()`/`.relabel()`, once with overlay params and once without, to produce `leaf` and `unadjusted_leaf` from one artefact.
- Overlay thresholds are TreeConfig `{"param":…}`s, so node keys cannot change under an overlay (§5.4.3 item 6).
- `test_walker_agrees_with_treeconfig_leaf` cross-checks the two traversal engines on 6 records.

The gap is that the full path lives only in `walk()`. The emitted evidence record carries the leaf, not the ordered node sequence (§5.4 "Emits"), so path capture is out-of-band rather than part of the decision.

Neither implementation used `branch` for absolute suppression. It is the natural built-in for "no evaluation should occur" (§5.2 req 3), and Haiku's NOTES wrongly says decider lacks `branch` and `loop`.

## 5. Spec coverage and struggles

**Haiku (coverage 2).**
- Trees: 60, but 15–99 nodes (2 430 total against about 9 200), each a single `feature > 20..80` test.
- Missing: §5.9 validation (explicitly "out of scope", although SCOPE requires it), a working identity map (it first-matches condition text anywhere in the tree), the volume dial and cut-off shift, `unadjusted_leaf`, and any 1 M-row run.
- Every struggle is agent capability. It never got past the `str`-literal kernel error, modelled a per-row engine as dict plumbing, and ignored TreeConfig.

**Sonnet (coverage 4).**
- Trees: 60 in total (59 generated, 37–275 nodes, 6 451 nodes, plus the hand-built campaign 23).
- Built: a validator for unreachable nodes, AND-only contradictions, and unknown or prohibited features; a real identity map; both threshold overlays plus the cap reduction, with both answers recorded; review-date errors; and capacity-constrained arbitration with a reason for every non-contact.
- Gaps:
  - No 1 M-row run or 14.2 M extrapolation.
  - Absolute suppression does not short-circuit evaluation.
  - `overlay_errors` exists but is not enforced in the cycle.
  - An out-of-scope overlay is skipped silently, where §5.3.4 req 6 says it must fail the cycle.
  - The identity map over-flags. Moving node 6's threshold gives 1 changed, 6 added and 6 removed, because the change cascades to node 8, which is still reached unchanged from node 5. NOTES acknowledges this as a §13 Q5 trade-off.
  - The scale identity-map test compares a tree with itself.
- Its struggles are mostly real framework findings:
  - `path_output` is leaf-only.
  - Tree `params` are call-scoped, not row-scoped.
  - `_warm` cannot synthesise a `date`.
  - `emit()` cannot pass a raw input through, which forced the `_echo_step`s.
  - 00's closed `_TIGHTEN_RULES` is a gap in consumed code.
- Its spec findings (seven vs eight leaves in §5.3.3, and a Stage 5 that must precede Stage 3) are correct.
- It read framework internals and declared it.

**Framework issue surfaced by this judging.** The handler's `code_path` insertion is skipped when `code_path` is already on `PYTHONPATH`. A consumed project's same-named `pipeline.py`/`inference.py` then silently wins. This caused Haiku's build failure as written.
