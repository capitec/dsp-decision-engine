## 2. Similarity, and the key question: real decisions or hand-built data?

Both decompose the slice into the same six capabilities, because the spec forces that. The substance differs completely.

**Haiku operates only on hand-built data.**
- `governance.py` imports nothing from 00, 01, 03 or 05.
- Replay calls `_stub_flow` (`pipeline.py:117`), which always returns `{"outcome_code": "approved", "offered_amount": 100000}`.
- The `diff`, `swap_set` and `dead_logic` branches of `harness_step` run on empty lists (`pipeline.py:81-110`).
- Every test feeds literal dicts.
- The following are missing:
  - swap-set **attribution** (population, data, logic or overlay). `SwapSetAnalyzer` only compares two callables.
  - the stack-off run.
  - the "renewed / never fired" columns of the ageing report, which are hard-coded to `[]` (`:551-561`).
  - table, tree and scorecard diff.
- `decision_date` defaults to `missing_as(date.today())` (`pipeline.py:30`), and `OverlayRecord` defaults its dates to `date.today`. Both break the §5.15 "no today" rule that SCOPE puts on every slice.
- NOTES.md "What I would do next" #2–#3 openly says that wiring to real flows and using `assert_equivalent` are still to do.

**Sonnet genuinely replays and diffs real decisions from 01, 03 and 05.**
- `flows.py` loads each flow's real `pipeline.build(...)` under a distinct module name (`paths.load_pipeline`, using `importlib`). It loads their real `configs/0.1.0` documents and binds with `Engine().bind`.
- `evidence_store.capture` scores each flow's own `sample_request.json` plus deterministic variants.
- `replay.replay` re-scores the stored request with the recorded params and diffs every output field, using tolerance bands for money, rates, scores and other values.

My probe (a scratch script over the captured store) gave:
- Replay: all 26 decisions return `reproduced`. Tampering 03's `recommended_amount` by +1000 gives `not_reproduced` with `first_divergence=recommended_amount`.
- Diff: runs on 01's real `live_rules.json` (a TreeConfig) and 03's real rate card, tested for insert-mid-priority and reorder invariance.
- Stack-off: flips every `adjustment_stack_enabled` in the recorded params through the same implementation. `unwind_estimate` moved 1 of 9 decisions in 03, and 0 in 01 and 05.
- Combined register: 10 real overlays taken from 01, 03 and 05's `AdjustmentRegister`s. The ageing report at 2027-12-31 lists 4.
- Dead logic: runs against 01's 521-rule live catalog (482 dead in 9 records), 03's 52 waterfall rules and 05's roll-up rules.

Gaps in Sonnet against the spec:
- **Attribution is partial.** `attributed_swap_set` handles only params-shaped increments (logic and overlay). It has no population or data increment, so §10 item 20 is half met. Its test only asserts that the baseline moved 0.
- **The "first divergence" is alphabetical.** `replay.py:95` does `sorted(set(...))`, so the first diverging field is picked alphabetically, not in execution order.
- **Demo populations are degenerate.** All 9 fraud records share `action_code 50`, and all 8 business records share outcome 4. Swap-set and coverage results only move for 03.
- **Only replay is served.** The other five capabilities are a plain library. NOTES §4.1 argues that their nested outputs don't fit typed steps; I did not reproduce that claim.
- **05 dead-logic counts are inconsistent.** 05's coverage counts `worst-event`, an id outside its declared universe, as "dominant".

Sonnet is far closer to the spec.

## 4. Reuse

**Haiku: none.** DEPS lists 01–08 as hard dependencies, but there are no imports of any earlier project. The NOTES.md "referenced, not copied" means copied field names only.
- Built-ins: `step`, `flow`, `param`, `missing_as`. They are misused: it tries to take evidence as `dict | None = param(None)`. `Engine(pipeline=...)` is not the real API.
- Everything else is hand-rolled dataclasses.

**Sonnet: real.**
- It calls 01, 03 and 05's pipelines, and reads their `AdjustmentRegister`s and `due_for_review` (00's mechanism). It also reads `fraud_interdiction.rules.build_rule_catalog`, `loan_granting.waterfall.REGISTER` and the three reason registries.
- It reaches private attributes to do so: `register._all`, `registry._by_code`, and 05's `_ENTITY_OVERLAYS`, `_BUSINESS_OVERLAYS` and `_BUSINESS_ADJUSTMENT_SET_ID`.
- **False claim:** `diff.py:10` says it "Reuses `credit_core.rate_card.diff_cards` directly". There is no call. `diff_table_rows` is a reimplementation.

Built-ins against where they would have fit (the questions asked):
- **Sessions: neither uses them.** `Executable.session` with `break_at`, `value` and `set` would give §5.1's point of first divergence in execution order, which fixes Sonnet's alphabetical bug. It would also give a what-if or stack-off override without rewriting the params document.
- **`decider.testing.assert_equivalent`: neither uses it.** Haiku names it only as future work. It fits the replay and certification check: bit-identical across modes, NaN-equal. Sonnet pins `interpreted` and compares by hand. Its hand-written 3-way tolerance grading is justified, because `assert_equivalent` is exact-only.
- **`step_map` / `to_ir`: neither uses them.** Sonnet's three per-flow hard-coded rule universes and firing fields (`deadlogic.py:45-75`) could partly come from `step_map(pipeline)` node paths, for tree nodes and step-level dead logic. Per-rule firing inside a flat rule tree still needs the flow's own evidence fields, so that part of Sonnet's approach is legitimate.
- **ConfigStore: neither uses it.** Sonnet rebuilds replay from the mutable `configs/<version>/` directory (`flows.py:66`). The evidence records only a params digest, not the digests of the tree and table documents. If someone edits `configs/0.1.0/live_rules.json` in place, replay silently runs the new logic. `ConfigStore`/`JsonFileStore.read(version)` exists to supply immutable versions and is the natural fit for §5.1.
