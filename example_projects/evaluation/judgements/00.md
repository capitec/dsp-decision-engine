## 2. Similarity

Both implementations have one module per capability, a Flex Loan demo pipeline that runs income → deductions → norms → obligations → affordability → score → PD → grade → price, and synthetic tables. The resemblance stops there.

- **Haiku** is a plain-Python library of dataclass-returning functions (`core/*.py`). decider appears only in the pipeline wrappers, and all tables are dicts or formulas in code.
  - `core.dates.resolve_effective_dated` and `core.adjustments.apply_adjustments` are imported by `pipeline.py:10-12` but never called anywhere, and no test covers them.
  - Adjustments have no scope check, no tighten-only rejection (the `TIGHTEN_ONLY` enum is never read), no lapse record, no review surfacing and no stack-off switch.
  - The tax tables ignore the date. `tax_year` is unused, and the rate is a flat 20% (`deductions.py:45-52`).
  - The "full 96×55×12 rate card" is a formula (`rate_card.py:86-117`). No table exists, the cell id is computed, the term bucket is `(term-6)//2` against a 55-entry list, and there is no diff artefact.
  - `core.obligations` has no treatment matrix. Its pipeline wrapper just passes through an input called `monthly_payment_sum` (`pipeline.py:97-106`).
  - `decision_date = missing_as(date.today())` (`pipeline.py:35`) and `date.today()` in `stubs.py:122` break the "no today" rule.
  - Scorecard characteristics are hard-coded (`pipeline.py:141-145`: tenure fixed at 24, adverse events at 0).
  - None of §10 items 4, 6 or 8 is demonstrated.
- **Sonnet** makes each capability a set of decider steps.
  - Eight tables are `DecisionTableConfig`: tax, statutory and internal norms, calibration, risk grade, appetite, credit life, and the rate card.
  - The scorecard is a `ScorecardConfig` with param-driven bin edges.
  - Obligations is a `frame_step` with two-list dedup and ten treatment behaviours, returning the scalar plus parallel per-account lists.
  - Effective dating is an `EffectiveDatedSet.resolver_step()` whose version id is ANDed into the table match (`dates.py`, `expense_norms.py`). I checked it: moving `decision_date` from 2026-09-24 to 2026-10-02 switches `statutory_norm_cell_id` from `…@2025#10` to `…@2026#10`.
  - `AdjustmentRegister` covers scope, declared order, tighten-only rejection at definition, lapse versus review surfacing, a per-overlay evaluation trace, and stack-off through one `param`.
  - The full 63,360-row card is an external config document with `diff_cards`.
  - Gaps:
    - The rate card, calibration and grade tables carry only a version string. They are not effective-dated.
    - `FEE_CAPS` is declared but never used to select a cap (`fees.py:55`; not wired into the pipeline).
    - Two live majors were skipped, as SCOPE allows.
    - §10 item 6 is tested only as "score twice, compare".
  - Behaviour bug in the demo pipeline: the computed `instalment` is never fed into `affordability_verdict_code`, whose `proposed_instalment` defaults to `None` (`affordability.py:594-606`). I scored R500 000 over 6 months: instalment **R87 446**, max affordable **R7 228**, verdict 1, **outcome approve**.

The spec has no numeric worked examples that both could run. Sonnet is far closer to the spec on every library-wide mechanism SCOPE names.

## 3. Maintainability

**Haiku code.** It is short and readable, but the docstrings mislead. `affordability.py` claims "four modes, three answer shapes, monotone guarantee", yet `mode` changes nothing (`affordability.py:167-171`) and `rate_range_maximum=100.0` is a placeholder. Other problems:
- Dead imports and dead mechanisms.
- A stray `pipeline_simple.py` that the config actually belongs to.
- A bare `except:` in `calibration.py:43`.
- Policy numbers such as haircuts and norm amounts hard-coded instead of kept in params.

**Summary 00-haiku.md: 3/5.** Right about the step list, the hard-coded tenure and adverse events, the modes having no effect, and there being no outcome field. It got some things wrong:
- It says income uses a "tenure haircut". The haircut is per evidence tier, and `months_employed` is unused.
- It says the pipeline aggregates "existing bureau payment obligations". It actually passes through a `monthly_payment_sum` input, and the sample's `bureau_accounts_json` is never read.
- It frames the project as an approval engine rather than a shared library.
- It could not see that the pipeline does not build, or that dates and adjustments are dead code.

**Sonnet code.** Module docstrings tie every choice to a spec clause, and workarounds are commented in place (`rate_card.py:30-47`, `reason_codes.py:425-427`). The costs:
- It is long: 2 396 lines against Haiku's 1 402.
- `income.py` re-runs `_select_tier` in three separate steps, because each step has one output.
- The column-renaming bookkeeping in `pipeline.py` is heavy.
- `expense_norms.py:19` cites a test file that does not exist.
- NOTES claims four date-resolved families in the pipeline. There are three.

**Summary 00-sonnet.md: 4/5.** It reproduced all 13 steps with the correct formulas (discretionary income, max instalment, outcome rules) and the overlay semantics. It got these wrong:
- It calls the grid a "360-cell rate grid" twice. The file has 63 360 rows.
- It describes obligations as a plain sum of instalments, missing the treatment matrix and dedup.
- It invented a 0–1000 bureau-score range.
- It read the demo pipeline as the product rather than a library demo.

## 4. Reuse

Neither implementation had earlier projects to reuse (wave 0, DEPS.md), and both say so.

**Haiku.** decider use is `flow`, `param` and `missing_as` in `pipeline.py` only, and that pipeline never binds. Every table, scorecard and rule is hand-rolled Python where `DecisionTableConfig` or `ScorecardConfig` would fit. It makes sensible stdlib use of `decimal.ROUND_HALF_UP` in `rounding.py` and `uuid`.

**Sonnet.** It uses the built-ins listed in the YAML block and verified in code. `DecisionTableConfig` backs 8 tables across 7 modules (`grep` confirms). `ScorecardConfig` is in `scorecard.py:165`, `frame_step` in `obligations.py`, `bureau.py` and `exposure.py`, and `.named()`/`.relabel()` in `test_affordability.py:50` (§10 item 4, run twice with buffers 0.12 and 0.18).
- The one private-API use is the `_warm` monkeypatch.
- It uses the stdlib `statistics` module for the variability ratio.
- No `branch`: eligibility collects every reason but does not short-circuit scoring (00 §6.15).

## 5. Struggles

**Haiku.**
- Params and pipeline got out of step. This is agent capability, made worse by the plain BRIEF.
- It never ran `decider build` yet claimed success. Agent capability.
- It used date/list/JSON-string inputs (`bureau_accounts_json`) to avoid ragged types. Agent capability.
- Its framework friction notes are generic. It gives no quoted errors, and the `_pii` metadata keys it mentions do not exist.

**Sonnet.**
- `_warm` fills `date` and `list` inputs with `1.0`, which forced a private monkeypatch. **Framework**; I verified it at `handler.py:198-206`.
- A `frame_step` returning list[struct] crashes materialisation, so it returns parallel lists. **Framework.**
- `missing_as([])` on an absent list column raises a ShapeError. **Framework.**
- List inputs arrive as numpy arrays, so `x or []` breaks. **Framework docs.**
- `DecisionTableConfig` allows only one open edge per table, so it uses ±inf per group. **Framework.**
- Compiled modes reject str-vs-str comparisons, which forces interpreted mode. **Framework**, but the error is clear.
- JSON dates are not coerced on the HTTP path. **Framework**, and not noticed by the agent.
- Unwired instalment → affordability, and unused `FEE_CAPS`. **Agent.**
- Ambiguous table sizing across SCOPE and 00 §8, and the 00/02 verdict ownership. **Spec.**
