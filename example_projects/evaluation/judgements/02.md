## 2. Similarity

Both implementations run the seven stages in order and try to sit on top of 00's affordability units. That is where the similarity ends.
- **Haiku** is one 130-line Python function (`assessment.py:97`) wrapped in a one-step `flow` (`pipeline.py:94`). Every request field is declared as a `param()` config value (`pipeline.py:14-34`), and `decision_date` defaults to `missing_as(date.today())`. That default is exactly the "select by today" defect class the spec (§5.3) warns about.
- **Sonnet** is a two-part `dag`:
  - `evidence_unit()` covers stages 1–4 and `capacity_unit()` covers stages 5–7. `build()` combines the same step objects (`pipeline.py:100-197`).
  - Per-applicant reuse of 00's income and deductions units uses `.relabel()` (`household.py:81-132`).
  - The buffer grid and the residual floor are `DecisionTableConfig` tables, and the output records cell ids.
  - Overlays use tighten-only `core.adjustments`.
  - Reasons are registry-backed.

Probes of behaviour on the spec's rules (I ran both):

| Rule | Haiku | Sonnet |
|---|---|---|
| Mode 1 (new application), any input | always `indeterminate`. It passes `payslip_income=None`, so every tier is "declared" (`assessment.py:118-123`) | correct pass / fail |
| Proposed instalment R99 999 in modes 2–4 | **`pass`** (the weak-evidence branch ignores the instalment, `assessment.py:193-199`) | `fail` (3) |
| Shape (b) with no capacity | `fail`. The spec allows only pass or indeterminate | `pass` / `indeterminate` only |
| Joint application, applicant 2 has no income | applicant silently dropped → `pass` (the spec's "worst available bug") | `indeterminate`, code 2 |
| Same account on both bureau and internal lists | counted twice (R2 000) | deduplicated (inherits 00's `_merge_accounts`) |
| Tax for 2020 / 2026 / 2033 | identical R5 100: a flat 20% in 00, and `tax_year` is ignored | effective-dated (R1 633.50 in 2025 vs R1 561.50 in 2026) |
| Buffer at grade 1 vs grade 12 | identical, hardcoded 12% plus R2000 + R500 per dependant | from the grid, 10–35% plus product loading |

Neither implementation can reproduce the spec's worked norm-table examples (R400 floor, the R25 000 band edge, R3M). Both 00 implementations ship a small flat-amount norms table instead of the 12-band fixed-plus-marginal table.

Sonnet's deviations from the spec:
- **Declared-only income passes a new application** (probe: `evidence_sufficiency_code 0`, pass). 00 numbers declared income as tier 4 (`credit_core/income.py:28`) and 02's new-application minimum is tier 4. In the spec, declared is tier 6.
- **In scenario mode a quoted account is imputed at quote/36** (`USE_SETTLEMENT_QUOTE`), not zeroed. The test name `test_settlement_quote_only_zeroes_...` claims otherwise (`test_household.py:54-69`).
- **Obligations do not implement the spec's treatments.** Dedup is exact-key, not the spec's 45-day / 5% match. `CONTINGENT`, `TERM_AWARE` and the `GREATER_OF` treatment are missing, and `REFER` is just type 99.
- **One required output is missing.** `living_expenses_unadjusted` is not emitted (26 of the 27 fields in §7). Haiku emits 23 of 27 and hardcodes `living_expenses_unadjusted = living_expenses`.

## 3. Maintainability

**Haiku.** Easy to read and easy to be misled by.
- Policy numbers are inline (`buffer_pct = 0.12`, `1.05`, `500*deps+2000`).
- Tier strings do not match between 02 (`"bureau_estimated"`) and 00 (`"bureau"`).
- The tests are largely vacuous. `test_monotonicity_in_instalment` runs in mode 1, where every verdict is `indeterminate`. `test_weak_income_evidence` accepts any verdict.

**Haiku summary: 3/5.**
- Right: it describes the stages and the buffer as `max(12%, floor)` correctly.
- Wrong: it says haircuts depend on "employment type and tenure" and that the buffer is "risk-based". In the code, the haircut depends on tier only and `risk_grade` is unused. It also says "PAYE", when the code applies a flat 20%.
- Missed: the always-declared tier and the ignored instalment outside mode 1.

**Sonnet.** Small modules with docstrings that cite spec sections, and constants that name what they mean. The friction is hidden in comments rather than in the code: the placeholder applicant-2 records, the private `_process` call, and the `_warm` monkeypatch.

**Sonnet summary: 4/5.**
- Right: the modes' minimum tiers, the buffer and floor race, the evidence-gate order and the overlay.
- Wrong: it echoes a `.named()` pattern that the code does not contain. It says court-ordered deductions are "merged with deductions" (they are subtracted in `discretionary_income`), and it describes statement expenses as an "override" rather than one of the higher-of bases.
- Missed: the evidence/capacity split that exists for separability, which is the key design point.

## 4. Reuse

**Haiku (partial).** It makes real calls to 00's `determine_income`, `calculate_deductions` and `apply_expense_norms` (`assessment.py:111-157`).
- 00's `calculate_obligations` and `core.affordability` are never imported, although NOTES says "All five affordability units are reused as-is".
- It does not use `core.adjustments`.
- 00's own units are thin: a flat 20% tax and a 4-band norms table. Much of the depth is therefore missing from both projects.
- NOTES also claims "all core functions mocked or stubbed". No mocking exists.

**Sonnet (real).** Unmodified use of 00's:
- `core.income` and `core.deductions`, each run twice via `.relabel()`
- the whole `core.expense_norms` unit
- `obligations._process`, which is private
- `affordability.discretionary_income`
- `adjustments.apply_stack_step`
- `reason_codes`, `rounding` and `evidence.cell_id`

It declines 00's flat buffer and verdict steps, with a stated reason (NOTES §5). It re-implements 00's dedup key in `household._dedup_within`, a small duplicate. Its claims check out:
- "12×6 buffer grid": 72 rows, from `_PRODUCTS` × 12 grades.
- "One acceptance test per mode": a parametrised test over 4 modes, though it only asserts that the verdict is in 1..4.
- "400-call loop": 400 capacity-only calls take about 3.6 s in interpreted mode against the spec's 900 ms. The test asserts `< 8000 ms`, and NOTES admits the looser bound. 400 full calls take 9.9 s, so the split gives roughly a 2.8× saving.

## 5. Struggles

**Haiku**
- **Agent capability.**
  - The PYTHONPATH order let 00's `pipeline.py` shadow its own, and it misdiagnosed that as a framework problem.
  - It modelled request data as config `param()`s.
  - Its tests never exercise decider.
  - It passes no payslip evidence to 00's waterfall.
  - Its NOTES overclaim what it did.
- **Framework.** The warm-up synthesiser's float-for-date gap would have blocked the build next. Sonnet hit the same gap and worked around it.
- **Upstream.** Haiku's 00 is too thin to carry the regulated arithmetic.

**Sonnet**
- **Framework.** The problems are documented with exact error messages:
  - An empty or absent ragged column, or a lone `None` scalar, crashes single-record scoring (`ShapeError` / `ArrowImportError`). The workaround is placeholder applicant-2 accounts, which then leak into the per-account annotation.
  - A `list[struct]` column cannot pass between two `frame_step`s. The workaround is calling 00's private `_process` directly.
  - The warm synthesiser cannot handle `date`, `list` or `dict` inputs. The workaround is monkeypatching the private `decider.serving.handler._warm` in `inference.py:236-243`.
  - Two smaller issues: the `missing_as(None)` guidance, and outer `.emit()` rejecting a passthrough column.
  - It had to run interpreted-only, because of a str-vs-str comparison inherited from 00.
- **Spec / upstream.** 00's income is single-source, its treatment codes differ from the spec's ten, and `core.bureau`'s shape does not match what DEPS.md says 02 consumes. Sonnet flagged all three honestly.
- **Agent capability.** It did not catch that its tier numbering disagrees with the spec, so declared income passes a new application.
