## 2. Similarity

Both implementations wrote the cap waterfall and the solve as plain Python functions over a hand-written rule list. Neither used `loop`, `TreeConfig` or a table for the cap register. That is where the resemblance ends.
- **Haiku** is a `flow` of 8 `@step`s returning `Dict[str, Any]`. It never reaches 00 or 02: `stub_evaluate_scorecard` returns a constant score of 600 and grade 7 (pipeline.py:20,153), affordability is a constant R4 350 (:34,222), and the rate is a linear function of grade (:43). EAR is set equal to the nominal rate (:263).
- **Sonnet** is a `dag` with the following parts:
  - 00's scorecard, calibration, risk-grade tables and `AdjustmentRegister` for the four §5.4.1 overlays, run in the declared order.
  - A 52-rule register: 13 named rules plus 39 generated fillers, at the spec's owner split.
  - 02's whole pipeline, called once per application.
  - Pricing from 00's 63 360-row card, loaded as a config document.
  - A banded top-down bisection solve.
  - Offer rules, dedup, the three objectives, and final validation.

**Client W's cap chain (§5.5).** I ran both waterfall functions on W's inputs.
- Both reproduce 500 000 → 150 000 → 120 000 → 76 000 → 95 000.
- Sonnet also gets term 72 (bound by CAP-0118) and worst grade 9 (bound by CAP-0210), both exact.
- Haiku leaves the grade at 12, because its CAP-0210 acts only on the amount. Its register has **12 rules, not 52** (caps.py `build_cap_register`).

**§5.8 solve.**
- Haiku scans down R100 at a time from the top and stops after 24 evaluations (solve.py:67). Any maximum more than R2 400 below the cap is never reached. On the band-edge test fixture and on a Client-W-like 24-month case, it returns `None` with BIND-EXH.
- Haiku's "named" non-monotone test passes only by accident. The solve returns `None`, and the assertion sits behind `if result.affordable_amount:` (test_granting.py:253). The assertion itself is `>= 48500`, so it would not catch R48 500 either.
- Sonnet's solve matched exhaustive search on 300 random cases on 00's card, and on the §5.8 worked-example card (19.75% below R50 000, 18.25% from R50 000).
- However, 00's card has rates that *increase* with amount and so has no inversions. On a card where every band edge is an inversion, Sonnet disagreed with exhaustive search in **65 of 300** cases, for example 60 months at R1 235.63 gave R37 500 against the true R38 600. The cause is the "proportional jump" (solve.py:197). It skips bands it never evaluates, even though the comment claims "Every band still visited is still fully verified". That is exactly the property §10 item 3 demands. None of the 300 cases exceeded 24 evaluations.

## 4. Reuse

**Haiku: stubbed.** No file imports `credit_core`, 00 or 02 (checked with grep). The `decider` built-ins are declared but never run, because the module fails to import. Every capability, including pricing, is a local stub.

**Sonnet: real.** I checked that these are actual calls, not just imports.
- **From 00:** `generate_flex_loan_card`/`rate_card_rate`, `fees.*`, `credit_life.*`, `instalment.*`, `rounding.*`, `build_scorecard`, the calibration and risk-grade tables, `AdjustmentRegister.apply_stack_step` (four times, relabelled), `consent_verdict_step` and `ReasonCodeRegistry.resolve_step`.
- **From 02:** the whole 02 pipeline, run as a nested `Engine().bind(...).score()` per row inside a `frame_step`. It is loaded through `importlib` because both projects name their entry module `pipeline.py` (affordability.py:51).
- **Hand-rolled where a built-in exists:** the rate lookup is a custom bisect `RateCardIndex` over the `DecisionTableConfig` rows, not the table step itself. That is justified by the 24-evaluations-per-term inner loop. The cap register could have been a data document.
- **Gaps inherited from 00:** EAR is nominal compounding, not an IRR including fees (pricing.py:194), so the §5.9 rule that suppresses offers above 60% EAR can never fire as the spec intends. There is no long-term loading table.
- **Not wired:** the rate add-on and cap overlays (`rate_addon_bps` defaults to 0 and is never passed). "Batch = real-time" is tested on 3 identical rows, not 100 k.
