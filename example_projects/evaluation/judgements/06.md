## 2. Similarity

The two agents agree only on the outline of the spec:
- the stage order: settleability, then settlement, baseline, generation, evaluation, selection;
- the empty set generated first, followed by H1 prefixes;
- products 11 and 20;
- the search written as plain Python instead of decider `loop`/`branch`.

**Haiku** is one `flow` wrapping a single 600-line module:
- pricing and affordability are stubbed;
- only H1 is implemented;
- only OBJ-02 is implemented;
- there are no overlays;
- "top 3" is just the first three viable scenarios (`consolidation.py:588`).

**Sonnet** is a `dag` of five stages (`pipeline.py:34-40`). The §5.4–5.8 search is one `frame_step` (`orchestration.py`) that:
- calls 02's pipeline **once** to fix the income and expense figures (§5.6.1);
- re-derives obligations for each scenario with 00;
- prices each scenario with 02's capacity and verdict functions and 03's `PriceEvaluator`, plus a fixed-point advance solve (6 iterations, R1 tolerance, `pricing11.py`);
- records a rejection code for every non-viable scenario (0 of 100 non-viable scenarios in the sample lack one) and an intervention result with actual and threshold values;
- blends objectives by weights, with a re-weight overlay (`objective_overlay_ids = ADJ-06-OBJ-2026-001,002` on the sample) and an anti-harm overlay tightening 15% to 12% on product 11;
- computes the indifference band, the shadow OBJ-05 best and a distinct top three;
- hands off to 03's real pipeline when the short-circuit applies;
- prices product 20 against a promotional and a reversion rate, over a paydown simulation, with a stressed payment.

The spec's worked examples cannot be compared, because Haiku always selects the empty set.

**Sonnet is much closer to the spec**, but it deviates in these places (checked in the code):
- **Nothing is configurable without code.** There is no `params.json`. Thresholds, objective weights, overlays and the budget are Python constants (`interventions.py DEFAULT_THRESHOLDS`, `objective.py`, `orchestration.py:34`), which breaks §5.8 requirement 1 and acceptance items 6 and 7. The comment at `inventory.py:184` ("overridable via params.json") is false.
- **Settleability order is wrong.** `inventory.py:104` tests "internal" before "secured" (l.110) and "revolving" (l.113), against the §5.2 order. The sample's internal card (account 2) comes out as code 0 instead of 8.
- **Product 11's minimum of 2 accounts is not enforced.** `search.py:110` routes sets of one account to product 11 and no check rejects them.
- **The tie-break is reversed.** "Fewest accounts settled" is coded as `-accounts_exited_proportion` (`objective.py:155`), which favours more accounts.
- **H6 duplicates H1** (`search.py:64`).
- **The settlement breakdown is dropped.** The per-component figures are computed but the frame step does not write them.
- **The overlay stack cannot be switched off from the pipeline.** `stack_enabled` is never passed in (acceptance item 10).
- **Two of product 20's own rules are missing**: "more than one revolving account in arrears" and "a balance transfer within 12 months".

## 4. Reuse

**Haiku: none.** No module imports `credit_core`, `assessment` or `granting`. The NOTES call these "planned but stubbed", but the code contains no stub calls, only hardcoded numbers. Built-ins used: `flow`, `param`, `missing_as`, and `param` is misused for request fields.

**Sonnet: real.** I verified these calls in the code:
- **Project 02:** its pipeline via `Engine().score` once per assessment (`baseline.py:81-93`), bound anew on each call. Its `capacity.max_affordable_instalment_before_overlay` and `verdict.affordability_verdict_code` once per scenario (`scenario_eval.py:414,462`).
- **Project 00:** `credit_core.obligations._process` once per scenario (`scenario_eval.py:371`), plus `adjustments`, `reason_codes`, `rounding`, `instalment` and `evidence.cell_id`.
- **Project 03:** `PriceEvaluator`, `RateCardIndex` and `CreditLifeIndex` (`pricing11.py:45-50`), and 03's full pipeline for the short-circuit. The test `test_short_circuit_hands_off_to_project_03…` covers that hand-off and passes.

On the built-ins: `DecisionTableConfig` serves only as a row container; lookups run through 03's Python index. No `param` is used anywhere. No tree, scorecard, branch or loop is used, which is reasonable for a per-record search.

Quantitative claims:
- "120 scenarios on the sample": verified (`search_consumption=120`).
- "~110 ms on the sample": I measured 196–273 ms warm.
- The "400 in 900 ms" test never reaches 400; it stops at `candidates_exhausted`. When I changed the test's 18-account client so that every account is a card, 300 scenarios ran in 399–477 ms. That suggests 400 would fit inside 900 ms.

## 5. Struggles

**Haiku.** All of these are agent capability:
- it never ran the mandatory build;
- it did not understand `param` vs input semantics;
- it integrated none of the consumed projects;
- its NOTES overclaim.

**Sonnet.** I checked each of these in the code:
- **Framework:**
  - `frame_step` cannot output `list[struct]`, which forced parallel lists and CSV strings;
  - the synthetic record in `_warm` cannot handle dates or lists, which led to a **monkeypatch of the private `decider.serving.handler._warm`** (`inference.py:44`);
  - the JSON input path does not turn date strings into dates, which is also partly an agent miss;
  - NOTES says `frame_step` cannot take `param()` overrides. That is a claim I did not verify.
  - NOTES 4.1 says a `list[struct]` with keys differing between records gives a `DTypePromotionError`. I could not reproduce it in a fresh process after removing a string key and then a date key.
- **Consumed-project gaps:**
  - 02's buffer and residual tables are published only as `DecisionTableConfig`, so Sonnet calls the **private `capacity._buffer_pct` and `_RESIDUAL_*`** (`scenario_eval.py:245-252`) and `obligations._process`;
  - 03's `solve_term` is locked to product 10 by its module constants.
- **Brief convention:** every project names its module `pipeline.py`, so they collide on import. Sonnet worked around it by loading them with `importlib` (`reuse.py`).
- **Spec:** the blend's scale across objectives, and new money not being a search dimension (Sonnet clamps it to CON-INT-08). NOTES.md declares both.
