## 2. Similarity

What they share: both generate the §6.1 counts exactly (521 live / 114 shadow, CF 214/31 … AA 58/12). Both keep a Python rule-catalog object with the governance attributes, and both have a separate action-resolution function. After that the two diverge completely.

- **Haiku** is a plain-Python library (`fraud_engine/rules.py`, `evaluator.py`) behind an unbound `flow`.
  - Rules are generated in code at request time with `effective_from = decision_date` (`rules.py:188`), so effective dating is a no-op.
  - Every predicate is `feature > threshold` (`evaluator.py:79`), including `beneficiary_age_hours` and `device_change_hours`, which inverts the spec's MS-0208 shape.
  - When I ran the library directly on its own sample event, and on an MS-0208-like mule payment, **0 rules fired** in both cases. Output was `action_code ALLOW` with `action_source_rule_id "HARD_BLOCK"`, which is a bug (`evaluator.py:223`).
  - All 521 rules apply to instant payments, CF included.
  - Tie-break is `(-action, priority)` only (`evaluator.py:190`). Severity, family and rule_id are missing.
  - Overlays are never applied: `overlay_stack=None` at `pipeline.py:164`.
  - There is no backtest, and 2 of the 6 hard-block gates.
- **Sonnet** compiles rule shapes into three `TreeConfig` `prioritized_flat_rule` documents with `mode="all"`: live, shadow, and an overlay-base re-evaluation (`rules.py:383-418`).
  - A `frame_step` joins the per-rule `.fired` columns with the catalog (`firing.py`). Shadow isolation is structural: `action_resolution.py` never reads `shadow_fired_rule_ids`.
  - The threshold overlay is a `ComputedFeature` (`amount - 8000*multiplier`).
  - All 6 gates, the degraded-mode bitset and mode, and backtest mode are present.
- On the spec's worked examples, only Sonnet runs. The 1.4× dial gives a multiplier of 0.7143, so R8 000 → R5 714. The dial applies on 2026-03-12, and the festive ×0.7 lapses by 2026-01-16 (`applied_adjustment_ids=[]`). Sanctions forces 60 while all 31 firings are still recorded. Stale velocity leads to `restricted`.

Sonnet is far closer to the spec. Its deviations:
- `primary_reason_code` is the registry's top-ranked code (3002), not the winner's (AT-0109 → 2029). §5.12 item 6 says it should be the winner's.
- Runners-up, per-family applicable counts, out-of-scope overlays and the list of degraded-mode-suspended rules are not recorded.
- There are no compensating rules and no fail-closed hold behaviour.
- The "sensitivity dial" is a second multiplier on the same MS amount threshold, not every tunable in the family.
- There is no 900-rule test; `test_rules.py:43` checks 635 rules.

## 3. Maintainability

**Haiku.**
- The library is small and readable, with clear dataclasses. But `pipeline.py` misleads: it shows commented `# @step` markers, `param()` used for per-request values (`action_code=param(10)`), and imports of `rank_reasons`, `resolve_effective_dated` and `apply_adjustments` that are never called.
- `evaluator.py:201` has a stray `from sys import path` and the comment "Rank reasons (will use core.reason_codes later)".
- Tests are shallow. For example, `test_action_precedence_by_severity` resolves a single rule and asserts only that an action exists.

Haiku summary (3/5):
- Right: the step order, and that overlays are stubbed (`overlay_stack` always None).
- Wrong: it calls `reason_codes` "ranked" (they are not), and says resolution sorts by "severity" (it sorts by action value, then priority).
- Missed: the pipeline cannot bind, predicates are inverted and nothing fires, and rules are generated in code.

**Sonnet.**
- Modules map one-to-one onto spec sections, with docstrings that cite §-numbers. It is verbose: long rationale comments, and `pipeline.py:21-29` is a nine-line comment on one import.
- The governance metadata (severity, action, priority, critical) is regenerated in code from a seed in `build()` (`pipeline.py:46`). Only the predicate shapes live in `configs/`, so changing a rule's action or severity needs a code deploy. That works against §6.1's analyst-owned attributes and the BRIEF's rule that thresholds belong in config. NOTES admits the coupling.

Sonnet summary (4/5):
- Right: the degraded mode, hard blocks, the three overlays, structural shadow isolation, the counterfactual, and the catalog/document coupling.
- Wrong: it says a governance exception "skips non-critical rules in that family". That conflates the critical-allow suppression with the exception flag (`action_resolution.py:55-60`).
- Missed: backtest mode entirely, and that the rules run on `TreeConfig` `mode="all"`.

**Sonnet.** I verified the main framework claims.
- **Framework problems:**
  - `Engine.run()` panics on a batch where a `list[str]` column mixes empty and non-empty rows. I reproduced this with Sonnet's 8-line repro: `PanicException ... SchemaMismatch ... expected String, got object`. Because of it, backtest runs `score()` per event.
  - `_warm` synthesises `1.0` for `date` and `list` inputs (visible at `decider/serving/handler.py:198-206`). This forced the private-API monkeypatch.
  - `frame_step` gets no `param()` bundle, so a scalar step carries the toggle as a column instead.
  - The `tree` type only registers if `decider.steps.trees` is imported.
  - Compiled mode rejects comparing a `str` column to a literal, so the project is served in interpreted mode.
  - `.emit()` of raw input columns is confusing.
  - The HTTP path does no JSON→`date` coercion. The agent did not notice this; it could have fixed it in its own `Handler.input_fn`.
- **Spec problems:**
  - The family precedence order is never published. §5.12 names it but gives no order.
  - It is unclear whether CF/FP volume should apply to instant payments.
  - It is unclear whether a hard block floors the counterfactual.
- **Agent capability:** `primary_reason_code` is not the winner's reason, the governance metadata is not in config, and there is no 900-rule point. Backtest equivalence runs through the same executable in both paths, so it is close to tautological; it proves determinism, not replay from stored records.
