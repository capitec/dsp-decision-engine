## 2. Similarity

The only things the two share are the P01–P18 naming, eight entry points with 2–8 stubbed, L1 bounded at 4 passes, and P15 skipped. The architectures are opposite.

**Haiku**
- The whole of EP1 is **one `@step`** (`pipeline.py:34`). It calls 18 plain functions that mutate a 60-field `DecisionState` dataclass (`flow_state.py`), so decider sees a single opaque node.
- Request fields such as `amount`, `gross_monthly_income` and `has_bureau_consent` are declared as `param()` (`pipeline.py:36-49`). They come from config, not from the request.
- `build(entry_point_code)` returns a different flow per entry point. The other entry points are docstring-only stubs.

**Sonnet**
- It is a real `dag` of about 34 members, with phase sub-dags named `p03`, `p06`, `p08`, `p09a`, `p10`, `p12` and `p18` (`pipeline.py`). This gives per-phase params namespaces.
- L1 uses `decider.loop` with carries (`consolidation.py:138`).
- Declared registries:
  - `phases.py`: the decision-point counts sum to 1 400 and match spec §5.1.
  - `entry_points.py`: the §5.20 matrix, which I checked row by row against the spec for EP 3, 4, 6 and 7, plus a content-derived `phase_set_id` with an inverse.
  - `shared_intermediates.py` and `ordering.py`.

**Behaviour on the spec's worked examples**
- Sonnet reproduces Client V's cap chain: CAP-0301 binds at R112 000 (spec line 1109; `test_cap_waterfall.py:15`).
- Sonnet reproduces the R60 000 band-edge inversion of §5.14 (`test_solve.py:28`).
- Sonnet's sample is not Client V's full input set: its income is R18 500, not R31 400. So its final offer differs from the spec's "R95 000 @ R2 717.16, BIND-REQ".
- I called Haiku's step function directly:
  - It approves R95 000/60 while hard-coding `binding_constraint: "affordability"` (`phases.py:541`).
  - Lower income gives a *better* grade: income 6 000 gave grade 1, while 18 500 gave grade 2. The cause is score = base + income adjustment, fed into an increasing-PD formula (`phases.py:296-310`).
  - L1 ran 4 identical passes (`loop_pass_count` 3), because P14 is a no-op that changes nothing (`phases.py:555-580`).

## 3. Maintainability, and how each organised a very large project

**Haiku: three flat files.** `phases.py` is 744 lines of every phase. Its docstrings claim things the code does not do:
- "188 rules": P05 just echoes a `fraud_verdict_code` argument.
- "14 assertions": P17 has 5.
- A degraded mode: `identity_degraded = False` is hard-coded at `phases.py:116`.

It also uses `date.today()` and `datetime.now()` for `decision_date` and `decision_id`, which breaks replay. And it calls `param(False)` inside a function body (`phases.py:150`).

None of the scale mechanisms the spec asks for exist:
- no ownership map;
- no ordering constraints beyond the order the code is written in;
- a `phase_set_id` that is just a per-entry-point string, and does not reflect conditional P14.

**Sonnet: a package with one module per phase**, plus five cross-cutting registries and a single composition root (`NOTES.md` "How I organised a large project"). The names map one to one onto spec sections, and every module docstring says what is real and what is stubbed.

Weaknesses:
- The registries are documentation, not derived from the pipeline. `test_ordering.py:10` checks a hand-maintained `_EXECUTED_ORDER` and skips every CYCLE constraint. `test_shared_intermediates.py` checks only the registry's own contents, even though its docstring says it is checked "against what the pipeline actually wires".
- The L1 body re-implements the affordability arithmetic inline (`consolidation.py`, as its own docstring says).
- The tables are generated in code rather than kept under `configs/`: the 34 560-cell card at `pricing.py:80` is 40 terms × 12 grades × 72 amount bands. This contradicts BRIEF's "keep tables in config documents", though `NOTES.md` admits it.
- One test is vacuous: `test_price_one_matches_the_wired_credit_life_table` only asserts `expected_rate > 0`.
- The docstrings are very verbose.

**Summaries**
- **Haiku summary, 3/5.** It correctly spots the stubs: the constant binding constraint, the loop that never updates obligations, and P14. But it repeats docstring aspirations as facts ("620+ rules", "14 assertions", "degradation handling"). It also misses that nothing uses 00 and that the inputs are params.
- **Sonnet summary, 3/5.** The phase order matches the code, including P16 before P12. But it invents a P04 "exclusion list", which is not in `acquisition.py`. It folds P07 and P11 away. It admits it did not read `solve.py` or `consolidation.py`, and misses the registries, the two-version `existing_obligations`, and the `_warm` monkeypatch. The summariser skimming only `pipeline.py` suggests the entry point is readable but that the depth sits in modules too long to skim.

## 4. Reuse

**Haiku: none.**
- `phases.py:13` inserts a non-existent path (`10-retail-credit-e2e/00-shared-credit-core`), and no module imports anything from `core`.
- `NOTES.md` says "All core.* capabilities available … Imported but not deep-integrated". That is false.
- Built-ins actually used: `step`, `param` and `flow`. The `loop`, `branch` and `missing_as` imports are unused. There is no table, scorecard or tree config.

**Sonnet: real, verified by call sites.** It calls `credit_core` at runtime:
- `income`, `deductions`, `expense_norms` and `obligations`, all wired in `_p06_unit`;
- `affordability.discretionary_income_step`, plus `max_affordable_instalment_step` relabelled at `affordability_phase.py:150`;
- `eligibility`, `consent`, `fees`, and five `instalment` steps;
- `rounding`, `credit_life`, `adjustments.AdjustmentRegister` (one register, five call sites), `reason_codes.ReasonCodeRegistry` (`disclosure.py:36`) and `evidence.cell_id`.

That is about 14 of 00's modules. `solve_advance_for_instalment` is imported but not used (admitted). It deliberately does not use 00's `rate_card` or `scorecard`: §1.1 and SCOPE ask for "10's own tables", so it uses `DecisionTableConfig` and `ScorecardConfig` directly.

## 5. Struggles

**Haiku**
- **Agent capability, the main cause:** unfamiliarity with the decider API. The invented CLI flags, `RequestHandler` imported from the wrong module, request fields declared as params, and the monolithic step returning a dict all come from this.
- It never ran `decider build`, although `NOTES.md` "Build and serve verification" claims ✓.
- The scope was stubbed nearly everywhere.

**Sonnet**
- **Framework:**
  - Warm-up cannot synthesise `date`/`list` inputs. The workaround is a monkeypatch of the private `decider.serving.handler._warm` (`inference.py:51`).
  - `list[dict]` step outputs crash materialisation, so the attribution chain stays outside the dag.
  - Repeated `adjustment_set_id` write collisions had to be relabelled one at a time.
  - `int` inputs arrive as `float`.
  - `str` table selectors force interpreted mode.
- **Environment / convention:** a top-level `pipeline.py` in both 00 and 10 forces a strict `PYTHONPATH` order.
- **Spec:** the P13 single-owner claim contradicts the §5.26.1 table; "applicable" in the cap register is undefined; the rate overlay in the solve conflicts with resolving the register once; segment precedence is unstated. These are all well founded.
- **Agent:** the HTTP path was left untested, which causes the date-string failure above.
